# 03 — 운전모드·변경사유 코드 체계

- 일자: 2026-08-24
- 상태: ✅ 완료 (`:libs:swtp-common:build` 통과, 테스트 6/6 + 위반 주입 실험 확인)
- 검토 관점: 없음 — 소환하지 않음(도메인 결정은 사용자가 내렸고, 남은 것은 그것을 코드로 옮기는 일이다)
- 리뷰: 미발동 — `/step` 발동 조건 4개(불변식 위반 · 다모듈 · `➖ 검증불가` 포함 · 기존 결정 뒤집음) 중 해당 없음. 코드 변경은 `libs/swtp-common`의 순수 신규 파일뿐이고, 02의 한계를 **해소**하는 것이지 뒤집는 것이 아니다
- 관련: `apps/master-service/docs/02-운전모드-변경이력-DDL.md`(이 작업을 「다음 단계」 2번으로 지목, 「알려진 한계」 6·7번을 여기서 해소), `docs/architecture/스마트정수장_리빌드_아키텍처.md` 11.3

## 발단

02가 `operation.drvmd_chg_h`를 만들면서 코드 컬럼 5개(`ctrl_trgt_type_cd`·`bf_drvmd_cd`·
`af_drvmd_cd`·`iss_svc_cd`·`chg_rsn_cd`)를 전부 제약 없는 문자열로 두었다.
그 문서의 한계 6번이 남긴 경고가 착수 사유다.

> 기존 `prcs_type_cd` 등도 같은 상태라 이 파일만의 문제는 아니나,
> **이력 데이터는 잘못 쌓이면 소급 정정이 불가능**해 일반 마스터보다 위험이 크다.

02는 이 작업을 **엔티티보다 먼저** 하라고 지목했다. 같은 이유다 — 엔티티가 붙는 순간 이력이 쌓이기 시작하고,
그 시점에 코드 체계가 없으면 정리할 수 없는 데이터가 남는다.

## 결정 (2026-08-24)

### 1. 운전모드는 "설비 상태 변경 명령을 누가 만드는가"의 축이다

3값으로 확정한다. 값의 의미는 사용자가 정의했다.

| 모드 | 코드값 | 의미 | 명령 생성자 |
|---|---|---|---|
| AI분석 | `AI_ANLS` | AI는 분석만 제공하고 현상태를 유지한다. 제어할 일이 생기면 사람이 제어한다 | 사람 |
| AI추천 | `AI_RCMD` | AI가 선택한 설비 상태를 사람에게 추천하고, 사람이 승인하면 그 상태로 변경한다 | AI 제안 → 사람 승인 |
| AI | `AI` | AI가 분석한 대로 설비를 운영한다 | AI |

**별도의 "수동" 모드를 두지 않는다.** `AI_ANLS`가 곧 수동이다.
아키텍처 11.3이 적어 둔 "자동/수동/원격"은 **제어 주체**의 축이고 이것은 **명령 생성자**의 축이라 다르다
("원격"은 접속 경로 축이라 아예 다른 이야기다). PLC의 로컬 인터록·시퀀스는 이 축이 규정하는 대상이 아닌
하위 레이어다 — 운전모드가 무엇이든 그것은 계속 돈다.

코드값은 `VARCHAR(10)`이 실질 제약이다. `AI_RECOMMEND`(12자)는 들어가지 않으므로
표준단어사전에 등재된 `RCMD`(추천)·`ANLS`(분석)로 조합했다.

### 2. 제어대상 유형과 무관하게 같은 모드 집합을 쓴다

`ctrl_trgt_type_cd`가 `CTRL_GRP`(EMS 송수펌프 제어그룹)든 `PRCS`(자율운영 공정)든 3값을 공유한다.
유효 모드가 대상 유형에 종속되지 않으므로 검증이 enum 하나로 끝나고, 조회·통계에서 두 축을 나눌 필요가 없다.

### 3. 상수명 자체를 DB 코드값으로 쓴다

별도 코드 필드를 두지 않는다. `CommonErrorCode`가 `INVALID_REQUEST("COMMON-400", 400)`처럼
문자열을 따로 가진 것은 `"COMMON-400"`이 하이픈 때문에 Java 식별자가 될 수 없어서다.
여기에는 그 제약이 없다.

- 필드를 두면 상수명과 코드값이 어긋날 수 있다 — 두 개를 동기화할 이유가 없다
- `@Enumerated(EnumType.STRING)`이 `name()`을 그대로 쓰므로 매핑에 변환기가 필요 없다
- `VARCHAR(10)` 제약이 상수명 길이로 자연히 드러난다 (검증 1번이 이것을 잡는다)

### 4. 변경사유는 11종으로 시작한다

| 구분 | 코드 | 언제 |
|---|---|---|
| 사람 | `OPRTR` | 특별한 사건 없이 운전원이 결정 — 가장 흔할 코드 |
| | `APRV` | 검증 결과를 확인하고 자율성을 올림 |
| 자동 강등 | `ANOMALY` | 공정값이 허용 범위를 이탈 |
| | `ITLCK` | 안전 인터록 발동 |
| | `MDL_DGRD` | 예측 오차가 임계를 넘어 AI 판단을 신뢰할 수 없음 |
| | `SNSR_FAIL` | AI **입력**이 오염됨 — 센서 고장·계측 이상 |
| | `COMM_FAIL` | `ai-service` 응답 없음 |
| 계획 | `SCHED` | 사전 정의된 시간대 전환 |
| | `MAINT` | 설비 점검·보수 |
| | `TEST` | 검증·시험 운전 |
| 기타 | `ETC` | 위에 없는 사유 — 비고 필수 |

**"최소로 시작해 늘린다"를 따르지 않았다.** 일반 마스터라면 그것이 맞지만 이력 테이블은 반대다 —
사유가 부족하면 전부 `ETC`로 몰리고, 나중에 코드를 추가해도 **이미 쌓인 `ETC` 행은 재분류할 수 없다.**
통계가 영구히 망가지는 쪽이 코드 3~4개를 미리 두는 것보다 비싸다.

특히 아래 셋은 AI 시스템에서 반드시 발생하므로 처음부터 둔다.

- `COMM_FAIL` — `ai-service`가 별도 FastAPI 프로세스다. 두절은 확정적으로 일어난다.
  논리적으로도 일관된다: AI가 응답하지 않으면 추천도 못 받으므로 `AI_RCMD`조차 유지할 수 없고,
  반드시 `AI_ANLS`로 떨어진다.
- `MDL_DGRD` — 모델은 계절·수질 변화로 성능이 떨어진다. `ETC`로 받으면 **재학습 시점을
  데이터로 판단할 수 없다.**
- `SNSR_FAIL` — `MDL_DGRD`와 구분하는 것이 핵심이다. **입력이 나쁜 것**과 **모델이 나쁜 것**은
  대응이 완전히 다르다(센서 교체 vs 재학습). 한 코드로 합치면 그 판단을 이력에서 복원할 수 없다.

`AI_ANLS`가 "AI 미개입"으로 확정되면서 **하향 사유가 곧 AI 신뢰도 지표**가 됐다.
"이상감지로 인한 강등이 월 몇 건인가"가 자율운영 성숙도의 1차 척도다.

**보류한 것** — `LOW_CONF`(신뢰도미달). AI가 스스로 "이번 판단은 확신이 낮다"며 내려가는 경우로,
`MDL_DGRD`(지속적 성능 저하)와 시점 성격이 다르다. 구분 실익이 확인되기 전까지 `MDL_DGRD`에 흡수한다.

### 5. 초기값은 `AI_ANLS`이고 초기 이력 행을 만들지 않는다

02의 한계 7번(`bf_drvmd_cd`의 최초 값)이 여기서 해소된다. **특수값이 필요 없어졌다.**

이력이 없다 = 한 번도 바뀌지 않았다 = `AI_ANLS`다. 첫 전환 행의 `bf_drvmd_cd`에 `AI_ANLS`를 넣으면 된다.
"대상이 언제 등록됐나"는 `master.prcs_m`·`ems.ctrl_grp_m`의 `rgstr_dttm`이 이미 답하므로
초기 스냅샷 행으로 중복할 이유도 없다.

무엇보다 **`AI_ANLS`가 안전한 기본값**이다 — 새로 등록된 설비가 등록되자마자 AI 제어를 받으면 안 된다.

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| `INIT`·`NONE` 같은 초기 코드를 모드 집합에 추가 | 운전모드가 아닌 값이 운전모드 컬럼에 들어간다. "설비가 지금 INIT 모드다"는 말이 성립하지 않는다 |
| 대상 등록 시 `bf=af=AI_ANLS` 이력 1행 삽입 | 변경 이력에 변경 아닌 행이 생긴다. 등록 시각은 마스터 테이블이 이미 갖고 있어 정보 이득도 없다 |

### 6. 전이 제약을 enum·DB에 박지 않는다

하향과 상향은 비대칭이다.

| 방향 | 규칙 |
|---|---|
| 하향(자율성 ↓) | 어디서든 `AI_ANLS`로 즉시. 인터록 발동 시 `AI` → `AI_ANLS` **직행이 반드시 가능해야 한다** |
| 상향(자율성 ↑) | 단계적(`AI_ANLS`→`AI_RCMD`→`AI`)을 권장하되 **강제하지 않는다** |

`AI_ANLS` → `AI` 직행을 막지 않는 이유는 정비 후 복귀처럼 이미 검증된 대상을 되돌리는 정당한 경우가
있기 때문이다. 막아 두면 그때 운영이 멈춘다. `bf`/`af`가 이력에 남으므로 사후 감사로 충분하고,
필요하면 UI에서 추가 확인을 받는 편이 낫다.

`DrivenMode`에 자율성 순서를 표현하는 최소 수단만 둔다(`level()`) — 방향 판정은 그 위에서 각자 한다.
**전이 허용 여부를 enum이 판단하지 않는다.**

### 7. 표시명을 담지 않는다

`ErrorCode`가 세운 계약을 따른다.

> 에러 메시지는 서버가 내려주지 않는다: 프론트가 코드값 기반 i18n으로 표현을 책임진다.

운전모드·사유의 한글 표시명도 같다. enum에 한글 필드를 두지 않는다.
DDL 코멘트를 한글로 쓰는 것(불변식 7)과 충돌하지 않는다 — 그쪽은 DB 문서화이고 이쪽은 API 응답이다.

### 8. 공통코드 테이블을 만들지 않는다

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| `master`에 공통코드 테이블 신설 | 운전모드는 **값과 동작이 결부**된다 — `AI`면 autonomous가 제어를 실행하고 `AI_RCMD`면 추천만 띄운다. DB에서 값만 늘려도 동작이 따라오지 않으면 무의미하다. 즉 "값 추가 = 코드 변경"이 본질이다. 사유 코드도 늘어나면 화면이 바뀌므로 어차피 배포를 탄다. 공통코드 테이블은 **정수장마다 다르거나 운영자가 직접 추가**하는 값에 값어치가 있는데 둘 다 해당 없다 |
| DA# `STD_CODE`에 등재 | 확인 결과 `STD_CODE`는 **0건**으로 아직 쓰이지 않는 체계다. 표준단어사전(`STD_DIC`)이 규제하는 것은 컬럼·엔티티 **이름**이지 코드**값**이 아니다. 다만 값을 등재 단어로 조합해 두면 나중에 `STD_CODE`를 채울 때 그대로 쓰므로 그렇게 했다 |
| 각 서비스가 자기 문자열 상수를 둔다 | 정의가 세 곳으로 흩어진다. ems가 `'AI_RCMD'`, autonomous가 `'AIRCMD'`로 쓰면 컴파일은 통과하고 이력만 오염된다 |

### 9. `libs/swtp-common`에 두는 것은 선택이 아니라 강제다

ems·autonomous·master 셋이 모두 이 코드를 쓴다(각자 자기 트랜잭션에서 이력을 기록하므로 — 02 결정 1).
그런데 앱 모듈 간 `project()` 의존은 `swtp.spring-boot-app`이 빌드를 실패시킨다(불변식 1).
따라서 `master`에 두면 ems가 쓸 방법이 없다.

`SwtpAuthMode`가 같은 이유로 여기 있다 — "게이트웨이와 각 서비스가 **같은 값을 같은 뜻으로** 읽어야 한다".

**문서를 `master` 쪽에 두는 것과 모순되지 않는다.** 무게중심은 파일 개수가 아니라 결정의 소유이고,
`operation` 스키마의 DDL 소유가 master이며 02가 이 작업을 다음 단계로 지목했다.

### 10. 모드 전환의 주체는 언제나 사람이고, `iss_svc_cd`는 2값이다 (2026-08-24 정정)

**착수 시점에 잘못 잡았던 전제를 사용자 확인으로 바로잡았다.** 초기 설계는 이상 감지·인터록·
통신 두절 시 **시스템이 자동으로 모드를 낮춘다**고 가정하고 있었다. 실제 설계는 그렇지 않다 —
운전모드 전환은 언제나 사람이 하고, 시스템이 스스로 낮추는 방어 로직은 **현재 없다.**
AI 서비스가 죽으면 명령이 나가지 않아 설비가 현상태를 유지하며, 모드를 내리는 것은
그 사실을 확인한 운전원이다. 자동 강등 도입 여부는 제어 경로를 붙일 때 함께 정한다.

세 가지가 따라 바뀌었다.

| 대상 | 정정 |
|---|---|
| `iss_svc_cd`의 의미 | "무엇이 발행했나" → **"사람이 어느 서비스에서 바꿨나"** |
| `IssuerService` 값 | `EMS`·`AUTO`·`MANUAL` → **`EMS`·`AUTO`** |
| `rgstr_id` | "운전원이면 그 계정, AI면 `SYSTEM`" → **항상 실제 운전원 계정.** `SYSTEM`이 들어갈 일이 없다 |

`MANUAL`을 뺀 이유는 `SwtpAuthMode`가 외부 IdP 값을 두지 않은 것과 같다 —
쓰이지 않는 값을 두면 **아무도 만들 수 없는 데이터를 위한 분기와 테스트**가 남는다.
아키텍처 11.3의 `issuer_service = 'autonomous' | 'ems' | 'manual'` 3값은 **제어 명령** 이력의 것이다.
거기서는 설비를 현장에서 직접 조작한 경우를 갈라야 하지만 운전모드에는 그런 경로가 없다.
공통 HMI 같은 제3 경로가 생기면 그때 더한다 — **빼는 것보다 더하는 쪽이 쉽다.**

**사유 코드 11종은 그대로 유효하다.** 다만 분류의 의미가 바뀌었다 —
`ANOMALY`·`ITLCK`·`MDL_DGRD`·`SNSR_FAIL`·`COMM_FAIL`은 "시스템이 자동으로 내린 조건"이 아니라
**"그 일이 생겨서 운전원이 내린 근거"** 다. 오히려 사람이 왜 내렸는지를 설명하는 사유라 더 자연스럽다.

**이 정정으로 약해진 근거 하나** — `ctrl_trgt_type_cd`를 별도 컬럼으로 둔 초기 근거는
"`iss_svc_cd='MANUAL'`인 행은 대상 종류를 판별할 수 없다"였는데 그 값이 사라졌다.
지금 두 컬럼은 값이 **1:1**이다(`EMS`↔`CTRL_GRP`, `AUTO`↔`PRCS`). 그래도 유지한다.
조회가 발행자로 조인 대상을 추론하기 시작하면 EMS가 공정 모드를 다루게 되는 순간
**조용히 깨지고**(컴파일도 쿼리도 성립하며 결과만 틀린다), 그 시점에 이미 쌓인 이력은
발행자로부터 대상 종류를 되돌릴 수 없다. 비용은 `VARCHAR(10)` 한 칸이고 위험은 되돌릴 수 없다.

## 구현 상세

패키지는 `com.mo.swtp.common.operation`을 신설한다 — 기존 `api`·`audit`·`observability`·`security`와
같은 층위이고, `operation` 스키마에 대응한다.

Lombok을 쓰지 않는다. 상수명이 곧 값이라 생성자·getter가 필요 없다 —
`CommonErrorCode`가 `@Getter @RequiredArgsConstructor`를 쓴 것은 필드를 가졌기 때문이다.

## 함정 기록

1. **`BUILD SUCCESSFUL in 1s`를 통과 근거로 삼을 뻔했다.**
   위반 주입 실험 후 임시 상수를 지우고 재빌드했더니 1초 만에 성공이 떴다.
   Gradle이 파일 상태를 실험 이전과 동일하다고 판단해 `test`를 **up-to-date로 건너뛴 것**이고,
   그때 읽은 XML은 이전 실행 결과였다. `--rerun-tasks`로 강제 실행하고 XML 갱신 시각을
   현재 시각과 대조해 확인했다(1초 차). **빌드 성공과 테스트가 실제로 돈 것은 다르다**는
   ems 01의 교훈이 이번엔 "캐시" 형태로 다시 나타났다 — 결과 파일의 **타임스탬프**까지 봐야 한다.

2. **`STD_CODE`가 비어 있다는 것을 확인하지 않았다면 코드 체계를 잘못 세울 뻔했다.**
   DA# 표준 체계에 코드값 관리 테이블(`STD_CODE`)이 존재하기 때문에, 있는 줄 알고
   거기에 맞추려 했다면 불필요한 제약을 스스로 지웠을 것이다. 실측 결과 **0건**이었고,
   표준단어사전(`STD_DIC`)이 규제하는 것은 컬럼·엔티티 **이름**이지 코드**값**이 아니다.
   다만 값을 등재 단어(`RCMD`·`ANLS`·`APRV`·`MAINT`·`ETC`)로 조합해 두어
   나중에 `STD_CODE`를 채울 때 그대로 쓰게 했다.

3. **"시스템이 자동으로 모드를 낮춘다"는 전제를 확인 없이 깔고 설계했다.**
   사유 코드를 "자동 강등" 5종으로 분류하고, `rgstr_id` 코멘트에 "AI면 `SYSTEM`"이라 적고,
   `COMM_FAIL`에 "반드시 `AI_ANLS`로 떨어진다"고 썼다. **전부 시스템 자동 전환을 가정한 서술**인데
   실제 설계는 "모드 변경은 언제나 사람"이었다. 사용자 확인으로 드러나 결정 10으로 정정했다.

   놓친 신호가 있었다 — `iss_svc_cd`에 `MANUAL`이 있다는 사실이 오히려 "사람이 바꾸는 경로가
   따로 있다"로 읽혀 자동 전환 가정을 강화했다. **11.3의 그 값은 제어 명령 이력의 것이지
   운전모드의 것이 아니었다.** 아키텍처 문서의 한 절에서 두 테이블을 함께 정의하고 있어
   컬럼 정의가 섞여 읽혔다.

   교훈: **"누가 이 행을 만드는가"는 스키마를 그리기 전에 확정해야 한다.**
   그것이 정해지지 않으면 컬럼 의미·코드 집합·감사 컬럼 해석이 전부 흔들린다.

4. **`ErrorCode`의 i18n 계약을 늦게 발견했다.** 설계 도중 "화면 표시명이 필요하니 enum에 한글을
   담자"고 판단했는데, `ErrorCode`가 *"에러 메시지는 서버가 내려주지 않는다 — 프론트가 코드값 기반
   i18n으로 표현을 책임진다"* 로 이미 계약을 세워 두고 있었다. 코드를 쓰기 전에 같은 층위의
   기존 파일을 읽어 바로잡았다. **관례는 CLAUDE.md보다 인접 코드에 더 자주 적혀 있다.**

## 알려진 한계

1. **아직 아무도 이 enum을 쓰지 않는다.** 이번 범위는 코드 체계 정의뿐이다.
   ems·autonomous·master의 엔티티와 write 경로가 붙어야 실제로 검증된다.
   특히 `@Enumerated(EnumType.STRING)` 매핑은 엔티티가 생길 때 처음 동작한다.
   → **무효가 됐다**(해소가 아니다): `04`의 결정 1이 "엔티티가 아니면 JdbcClient"를 확정하면서
   이 테이블에는 엔티티가 생기지 않게 됐다. `@Enumerated`는 쓰이지 않으며, enum ↔ 문자열 변환 책임은
   `DrvmdChgRepository`의 RowMapper로 옮겨갔다. **enum 자체는 04에서 처음 실제로 쓰였다.**

2. **DB가 코드값을 강제하지 않는다.** V3에 CHECK 제약을 걸지 않았고(02 결정 5) FK도 없다.
   `INSERT ... VALUES ('AIRCMD')` 같은 오타는 DB가 받는다. 그물은 애플리케이션의 enum뿐이며,
   그 enum을 우회하는 네이티브 쿼리·수동 DML은 걸러지지 않는다.
   **이력 데이터는 소급 정정이 불가능하므로** 엔티티 착수 때 이 경로를 점검해야 한다.
   → **읽기 쪽 그물은 04가 쳤다**: `04`의 결정 6. 조회 시 코드 체계 밖 값을 만나면
   `hist_id`·컬럼명·값·허용 목록을 담아 예외를 던진다(04의 검증 7이 위반 주입으로 확인).
   **쓰기 쪽은 여전히 비어 있다** — write 경로가 생길 때 같은 그물을 그쪽에도 쳐야 한다.

3. **전이 규칙이 코드로 표현되지 않았다.** 결정 6에 따라 `level()`만 두고 허용 여부는
   서비스 계층에 맡겼다. 즉 지금은 **어떤 전이도 막히지 않는다.**
   "하향은 즉시, 상향은 단계적 권장"이라는 정책은 문서에만 있다.
   모드 전환 API가 생길 때 그 계층에서 구현하고, 그때 `AI_ANLS` → `AI` 직행에
   추가 확인을 요구할지 정한다.

4. **`ETC` 사용 시 비고 필수를 강제하지 않는다.** `chg_rsn_rmrk`는 NULL 허용 컬럼이라
   `ETC` + 비고 없음 조합이 DB를 통과한다. Javadoc과 DDL 코멘트에 "반드시 함께 남긴다"고
   적었을 뿐이다. 서비스 계층 검증(`@AssertTrue` 등)이 필요하며 2번과 같은 시점에 붙인다.

5. **`LOW_CONF`(신뢰도미달)를 `MDL_DGRD`에 흡수했다.** AI가 특정 시점의 추론 신뢰도가 낮아
   스스로 내려가는 경우와 모델의 지속적 성능 저하는 대응이 다르다(재시도 vs 재학습).
   구분 실익이 확인되기 전에 코드를 늘리지 않았으나, **그동안 쌓인 이력은 둘을 구분하지 못한다** —
   결정 4가 경계한 소급 재분류 불가 문제를 이 항목만은 감수한 셈이다.
   자율운영 운영 데이터가 쌓이면 가장 먼저 재검토할 항목이다.

6. **아키텍처 11.3과 실물이 계속 어긋나 있다.** 이번에 운전모드의 정의는 확정했으나
   11.3의 `operation.operation_mode -- 공정별 운전모드 (자동/수동/원격)` 서술은 그대로 두었다.
   "현재 모드" 조회 테이블을 별도로 둘지가 미결이기 때문이다(02 한계 8번).
   그 결정과 함께 11.3을 고쳐야 하며, 지금은 **문서가 존재하지 않는 값 집합을 말하고 있다.**
   → `04`의 결정 4가 "현재 모드 테이블을 두지 않는다"로 미결을 닫았으나 **11.3 수정은 하지 않았다.**
   이 한계는 그대로 이월된다(04의 알려진 한계 6).
