# 01 — 앱 내부 패키지 규약 확정과 master-service 적용

- 일자: 2026-08-24
- 상태: ✅ 완료 (빌드 통과. 컨테이너 E2E 미실행 — 아래 「알려진 한계」)
- 관련: `apps/CLAUDE.md` 「패키지 규약」(규칙 본문의 SSOT), `docs/scaffold/steps/step-18`(규약 통일 선례)

## 발단

앱 내부 자바 패키지 구조에 대한 **플랫폼 차원의 결정이 없었다.** 문서화된 것은
`apps/master-service/CLAUDE.md`의 한 줄("각 도메인은 `domain`·`dto`·`service`·`web` 4패키지로 나눈다")뿐이었고,
그건 규약 선언이 아니라 한 앱의 관찰 기록이었다. 실제로는 세 방식이 공존했다.

| 앱 | 배치 |
|---|---|
| master-service | `master/{tag,prcs,eqp,fclt}/{domain,dto,service,web}` (2단) |
| auth-service | `auth/{api,config,key,token,user}` (도메인 우선이나 레이어 분할 없음) |
| gateway / realtime-service | `{filter,security}` / `{stream}` (도메인 없음) |

`docs/architecture/`의 21개 장에도 패키지 구조 장이 없다. **ems·pms·autonomous 스캐폴드 3개가 아직 `Application`
클래스뿐이므로, 지금 정하지 않으면 셋이 각자 다른 형태로 자란다.**

그리고 규약 부재가 만든 결함이 이미 코드에 있었다(아래 「발견한 결함」).

## 결정 (2026-08-24)

### 1. 도메인 슬라이스 우선 — 형(型)을 셋으로 나눈다

규칙 본문은 `apps/CLAUDE.md` 「패키지 규약」에 두고 여기 복제하지 않는다. 요지만:

- **A형(2단)** 도메인 2개 이상 — master-service. `<도메인>/{web,service,repository,dto,domain}` + 앱 레벨 `support`/`query`/`event`
- **B형(1단)** 도메인 1개 — auth·telemetry·job. 도메인 세그먼트를 생략한다
- **대상 외** 도메인 상태 없음 — gateway·realtime·config-server·discovery-server

**"전 앱 통일"을 하지 않은 이유.** step-18은 게이트웨이 경로 규약에 "예외를 두지 않는다"고 못박았지만,
그건 **외부 계약**이라 이탈이 프론트 주소·화이트리스트·문서 URL·티켓 경로 네 곳으로 전파됐기 때문이다.
패키지 배치는 앱 내부이고, 루트 불변식 1(앱간 `project()` 의존 금지)이 전파 경로를 이미 끊어 놓았다.
realtime(4파일 126줄)에 빈 `domain/`·`repository/`를 만들면 "규약을 따르는 척하는 껍데기"가 남는다.

그래서 **예외가 아니라 "대상 외"** 로 선언한다 — 예외는 "대상인데 안 지킴"이고 이건 "대상이 아님"이다.
같은 이유로 B형 3개 앱의 미적용은 `apps/CLAUDE.md`의 적용 현황 표에 ⬜로 남겨 **"아직 안 끝난 상태"** 임을 드러낸다.

### 2. `repository`를 `service`에서 분리한다

기존에는 `tag/service/TagRepository.java`였다. 문서가 선언한 4패키지에 `repository`가 없는데 현물이
`service` 안에 있었으니, **문서 규약이 이미 한 번 지켜지지 않은 상태**였다.

지금 분리하면 4파일 이동으로 끝난다. telemetry·job이 실도메인을 붙이면 JdbcClient `@Repository` **클래스**와
SQL 텍스트 블록이 들어오는데, 그때는 `service/`에 업무 흐름과 SQL이 섞인 상태에서 되돌려야 한다.

### 3. `dto` 패키지는 존치하고, `XxxDtos` 중첩 컨테이너만 해체한다

`dto`를 `web`으로 흡수하는 안(Request/Response는 web 계약이므로)을 검토했으나 **기각**했다.
이 결정은 `service`가 `dto`의 Response를 반환하는 현 구조를 **허용으로 남기는 것**과 짝이다.

**해체의 결정적 근거는 취향이 아니라 OpenAPI다.** 해체 전 master 한 스펙 안에
`AddRequest`·`AddListRequest`·`ModifyRequest`·`ModifyListRequest`가 **필드 구성이 서로 다른 채 4벌씩** 있었다
(`TagDtos.AddRequest`는 3필드, `EqpDtos.AddRequest`는 6필드). springdoc은 중첩 record도 단순 클래스명으로
스키마를 등록하고 `springdoc.use-fqn`은 리포 어디에도 설정돼 있지 않으므로, 넷이
`#/components/schemas/AddRequest` 한 칸을 두고 다툰다.

> **이 충돌은 실측하지 않았다.** 컨테이너가 떠 있지 않아 확인하지 못했다 — 「알려진 한계」 참조.
> 다만 해체의 나머지 근거(와일드카드 import 제거, 타입 이름의 전역 유일성)는 실측과 무관하게 유효하므로
> 결정은 바뀌지 않는다.

`springdoc.use-fqn=true`로 우회하는 안도 있었으나, 스키마 이름이
`com.mo.swtp.master.tag.dto.TagDtos$AddRequest`가 되어 프론트 타입 생성기가 험한 이름을 받는다.

### 4. `Command` record를 도입하지 않는다

`service`가 `web` 계약을 받지 않게 하는 장치인데, 결정 3에서 **`service → dto` 의존을 허용**하기로 했다.
둘을 동시에 취하면 `TagAddRequest` → `TagAddCommand`가 필드 대 필드 복사만 하는 빈 의식(ceremony)이 된다.

**대신 탈출구를 규칙으로 남겼다** — `apps/CLAUDE.md`에 "`service`가 반환한 Response 타입을 Kafka 페이로드로
재사용하지 않는다"를 명시했다. `master.changed` 토픽은 이미 생성돼 있고 소비자(telemetry·AI)가 붙을 예정이라,
이 한 줄이 없으면 `publishEvent(TagResponse.from(tag))`가 가장 자연스러운 손놀림이 되고
그 순간 REST 응답 스키마가 토픽의 와이어 계약이 된다.

### 5. 강제 장치를 두지 않는다 — 문서와 리뷰뿐

ArchUnit(`libs/swtp-arch-rules` + testFixtures로 룰 1벌 공유)과 convention plugin의 디렉토리 검사 둘 다 검토했고,
**둘 다 이번에는 도입하지 않는다.**

**이 결정의 위험을 그대로 적어 둔다.** 이 리포에서 같은 방식이 이미 한 번 실패했다 —
4패키지 규칙이 문서에 적힌 상태에서 Repository가 `service/`에 들어갔다(결정 2). step-18 함정 #4도
*"문서에 적어 뒀는데 지켜지지 않은"* 항목을 다뤘다. 즉 **문서 규약의 준수율이 이 리포에서 이미 반증돼 있다.**

그래도 이번 배치가 ArchUnit 도입을 막지 않도록 형태를 맞춰 뒀다 — `apps/CLAUDE.md`의 의존 방향 항목이
그대로 룰 1:1로 옮겨 갈 수 있는 문장들이고, 붙일 시점은 `check`다
(`build-logic/CLAUDE.md`: "어겨서는 안 되는 상태"인지 "아직 안 끝난 상태"인지로 판정 — 수렴 중 중간 상태는 정상이다).

### 6. `common` → `support`, `ColLength`는 쪼개지 않는다

`common`은 무엇이든 들어갈 수 있는 이름이라 신(god) 패키지가 되는 경로다. `support`를
**"도메인을 모르는 잎(leaf)"** 슬롯으로 정의하고 규칙에 그렇게 적었다.

`ColLength`가 TAG_SN·FCLT_ID·EQP_ID·PRCS_ID를 한 클래스에 모아 도메인 경계를 가로지르는 것은 사실이지만
**쪼개면 성립하지 않는다.** `tag/domain/EqpTag`가 `EQP_ID` 길이를 쓰는데, 도메인 간 참조 금지 규칙에 걸려
`eqp` 쪽 상수를 읽을 수 없다. 그리고 이건 값이지 결합이 아니다 — 진짜 SSOT는 `V2__master_domain.sql`이다.

> 남은 부채: 엔티티 `@Column(length=)`와 Flyway DDL을 대조하는 테스트가 이 상수의 진짜 검증이다. 이번 범위 밖.

### 7. 교차 도메인 엔티티의 소유 판정을 규칙으로 적는다

기존 배치가 임의적이라는 증거: `PrcsFclt`는 이름의 **왼쪽**(prcs)에, `EqpTag`는 **오른쪽**(tag)에 있었다.
규칙이 있었다면 방향이 같았을 것이다.

```
① 그 관계를 만들고 끊는 API를 소유하는 도메인에 둔다
② ①로 안 갈리면, PK가 한쪽 도메인의 키 단독인 쪽이 소유한다
```

`prcs_fclt_r`은 ①("공정에 시설을 편성한다")로 `prcs`, `eqp_tag_p`는 ①로 안 갈려 ②로 `tag`.
**둘 다 이미 옳은 자리에 있었다** — 이번에 더한 것은 배치 변경이 아니라 판정 근거다.
②가 취향이 아닌 이유: PK가 `tag_sn` 단독이라는 것은 "태그 하나는 설비 하나에만 귀속된다"는 불변식이
태그 쪽에 걸려 있다는 뜻이고(`V2__master_domain.sql:151-152`가 그렇게 적고 있다), 그 불변식을 지킬 쪽이 소유자다.

### 8. 도메인 간 타입 직접 참조를 금지한다 — 지금이 공짜다

`Eqp.fcltId`·`EqpTag.eqpId`·`PrcsFclt.prcsId/fcltId`가 전부 `String` 스칼라이고, `V2__master_domain.sql:20`이
*"FK 제약은 걸지 않는다 — 참조 정합성은 애플리케이션 책임"* 이라 적어 뒀다.
**DB 설계가 이미 이 규칙대로이고 자바 코드가 아직 그걸 말로 안 한 상태였다.** 현재 위반 0건이라 선언 비용이 0이다.
`@ManyToOne` 하나가 들어온 뒤에 못박으면 그건 스키마 논쟁이 된다.

포기하는 것: 조인 한 번이면 될 조회에 서비스 2회 호출 + 애플리케이션 조합이 든다.
얻는 것: 도메인을 다른 서비스로 떼어낼 때 컴파일러가 이미 끊어 놓은 상태를 준다.
그리고 이 규칙이 **엔티티를 트랜잭션 밖으로 내보내도 지연로딩 사고가 없는 근거**이기도 하다.

## 발견한 결함 (이번에 함께 고침)

규약 작업 중 드러난 것들이고, 전부 **패키지 규약과 무관하게 실재하던 결함**이다.

| # | 결함 | 왜 아무도 몰랐나 | 조치 |
|---|---|---|---|
| 1 | `TagController`의 `@GetMapping("/{tagSn}")`과 `@GetMapping("/{tagTypeCd}")`가 같은 URI를 매칭 | 패턴 **문자열**이 달라 등록 단계에서는 충돌하지 않는다 — 기동은 된다. 요청이 와야 `Ambiguous handler methods`가 난다. master는 실행 가능한 테스트가 0건 | 다른 3개 컨트롤러와 동일하게 `/type/{tagTypeCd}` |
| 2 | 같은 메서드의 `@PathVariable String tagTyCd`가 템플릿 이름(`tagTypeCd`)과 불일치 | 위와 같음 | 이름 일치 |
| 3 | `EqpTag extends BaseEntity` — `eqp_tag_p`에 `mdf_*` 컬럼이 없다 | `ddl-auto: none`이라 **기동 시 검증하지 않는다.** 첫 접근에서야 컬럼 없음으로 터진다. 아직 Repository가 없어 호출 경로가 없다 | `extends BaseCreatedEntity` (`V2__master_domain.sql:18`이 이미 지정해 둔 것) |
| 4 | `PrcsFclt`가 아무것도 상속하지 않는다 — NOT NULL인 `rgstr_*`에 감사 리스너가 안 붙는다 | 위와 같음. `validate`가 아니라 `none`이므로 "매핑 안 된 컬럼"은 검사 대상도 아니다 | `extends BaseCreatedEntity` |
| 5 | 전 파일에 `📄 FILE : null.java` / `📁 PACKAGE : ...master.api` 헤더 | IntelliJ 템플릿이 값을 못 채웠다. `PACKAGE` 줄은 이미 실제 경로와 달랐다 | 24파일에서 블록 제거. 새 파일에 붙이지 않는 것을 규칙화 |
| 6 | `jakarta.transaction.Transactional` 사용 (auth·job은 Spring 것) | 동작은 한다 — `readOnly` 옵션이 없을 뿐 | Spring `@Transactional`로 교체 |

> **결함 3·4에 대한 정정**: 조사 과정에서 "이것 때문에 master-service가 기동하지 않는다"는 판단이 한 번 나왔으나
> 사실이 아니다. `config-repo/application.yml:72`가 `ddl-auto: none`이라 Hibernate가 기동 시 스키마를 검증하지 않는다.
> (그 줄의 주석은 *"엔티티/스키마 불일치는 기동 실패로 드러낸다"* 라고 적고 있는데, 그건 `validate`의 동작이지
> `none`의 동작이 아니다 — **주석과 설정값이 어긋나 있다. 별건.**)

## 트랜잭션 경계 — 결함 6에서 파생된 필수 조치

`@Transactional`을 Spring 것으로 바꾸면서 클래스에 `@Transactional(readOnly = true)`를 걸었다.
그런데 **`addTag`·`addEqp`·`addFclt`·`addPrcs` 4개는 원래 `@Transactional`이 아예 없었다**
(`addXxxs` 복수형과 `modifyXxx`에만 있었다).

읽기 전용 트랜잭션은 Hibernate의 FlushMode를 `MANUAL`로 만든다. 클래스 기본값만 걸고 이 넷을 놔두면
**INSERT가 조용히 사라질 수 있었다.** 그래서 넷 모두에 명시적 `@Transactional`을 붙였다 —
부수 변경이 아니라, 이 작업이 만들 뻔한 버그를 막는 조치다.

**JSON 계약은 바뀌지 않았다.** record 이름만 바뀌고 필드 구성·요청 본문 형태는 그대로다.

프론트 계약 변경이라 손대지 않았다.

### 루트 `CLAUDE.md`를 건드리지 않은 이유

규약을 대상 4개 앱 중 1개만 따르는 상태에서 루트 불변식으로 선언하면,
`docs/sync/sync-01`이 D4에서 지적한 **"문서는 옳은데 현물이 어긋난"** 상태를 새로 만드는 셈이 된다.
step-18 함정 #4가 남긴 교훈("정합성 점검이 불일치를 무조건 문서 수정으로 해소하면 미완 작업이 기록상 완료로 바뀐다")의
반대 방향 실수다. B형 3개 앱이 수렴한 뒤에 올린다.

## 알려진 한계

1. **OpenAPI 스키마 충돌을 실측하지 못했다.** 컨테이너가 떠 있지 않아 작업 전후 스펙을 받지 못했다.
   결정 3의 근거 중 이 항목만 미검증이다. 다음 기동 시 확인한다:
   ```bash
   curl -s localhost:8081/api/master/v3/api-docs | jq '.components.schemas | keys'
   # TagAddRequest·EqpAddRequest·FcltAddRequest·PrcsAddRequest 가 각각 있어야 하고
   # 접두사 없는 AddRequest·ModifyRequest 는 없어야 한다
   ```
2. **매핑 결함 수정을 런타임으로 확인하지 못했다.** 빌드까지만 통과했다.
   `GET /api/master/tag/{tagSn}`과 `/api/master/tag/type/{tagTypeCd}`가 각각 200인지 확인해야 한다.
3. **교차 엔티티 상속 수정은 실행 경로가 없다.** `EqpTag`·`PrcsFclt`에 아직 Repository가 없어 INSERT가 일어나지 않는다.
   그 도메인 API가 생길 때 감사 컬럼이 실제로 채워지는지 확인해야 한다.
4. **강제 장치가 없다**(결정 5). 규약 유지가 리뷰에 의존한다.
5. **master 도메인 통합 테스트는 여전히 0건**이므로 `failOnNoDiscoveredTests = false`를 제거하지 않았다.
