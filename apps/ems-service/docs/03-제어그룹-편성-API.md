## 발단

[02](02-제어그룹-마스터-CRUD.md) 「결정 1」이 범위를 마스터 2종으로 한정하면서 편성 3종을 여기로 미뤘다.
그 결정의 근거는 **미증명 위험 3개 중 둘을 먼저 실증한다**는 것이었고, 02에서 둘 다 초록이 됐다.

| 미증명 항목 | 상태 |
|---|---|
| `CHARACTER(1)` + `@Enumerated(STRING)` 왕복 | ✅ 02에서 실증 (raw 값이 패딩 없는 `'N'`) |
| assigned-ID에서 `save()`가 `merge()`를 타는 문제 | ✅ 02에서 실증 (기존 ID 등록이 `EMS-409`로 끊김) |
| **같은 트랜잭션 delete-then-insert의 flush 순서** | **이번 범위** |

세 번째가 이번 작업의 핵심 기술 위험이다. 편성 저장은 **거의 항상** "대부분 그대로 두고 몇 개만 들고 나는"
형태라, PK가 겹치는 delete-then-insert가 예외가 아니라 **정상 경로**다.

관점 소환은 하지 않았다. 판정표상 새 테이블·Kafka·불변식이 걸리지 않고,
02에서 소환한 세 관점이 이미 편성 API를 겨냥해 답을 냈다 —
정수장 도메인은 replace-all·인질 문제·비활성 그룹 처리를, 데이터는 flush 경계와 벌크 DELETE 함정을,
분산 아키텍처는 컬렉션 전체 교체의 필연성을 각각 지목했다. 같은 입력으로 다시 띄우면 표만 는다.

## 결정 (2026-08-25)

### 1. 컬렉션 전체 교체(replace-all) — 개별 추가·삭제 엔드포인트를 만들지 않는다

세 관점이 서로 다른 근거로 같은 답에 왔다(02 게이트에서 승인됨).

| 관점 | 근거 |
|---|---|
| 정수장 도메인 | 편성 화면은 좌(가용)↔우(편성됨) 이동 후 **저장 버튼 한 번**이 표준형이다. 클릭마다 커밋되면 운영자가 화면을 중간에 닫았을 때 펌프 0대짜리 제어그룹이 남는다 |
| 데이터 | `ctrl_eqp_p`에 `mdf_*`가 없는 것이 이미 *"편성을 UPDATE 하지 않고 삭제 후 재등록한다는 선언"*(`V1__ems_domain.sql`)이다 |
| 분산 아키텍처 | 부분 수정 API를 노출하고 내부에서 전삭제-재삽입하면 **동시 요청 둘이 서로의 편성을 지운다** |

`PUT /api/ems/ctrl-grp/{ctrlGrpId}/{eqp|wnp|tag}` 하나로 그 그룹의 편성을 통째로 확정한다.
**빈 배열을 허용한다** — 편성 해제이자 아래 결정 3의 인질 해제 수단이다.

### 2. 뺏어오기(steal)를 허용하고, 빠진 곳을 응답에 실어 완화한다

**사용자가 직접 정한 것이다.** 정수장 도메인 관점은 **409 거절**을 주장했다 —
*"정수장에서 남의 계열 펌프가 소리 없이 빠지는 것은 사고다."*

**기각한 이유**는 409로 막으면 *"1계열 펌프를 2계열로 옮긴다"* 는 **가장 흔한 편성 변경**을
API가 표현하지 못하기 때문이다. 운영자는 "A를 빈 목록으로 저장 → B에 저장"의 2요청을 강요당하고,
데이터 관점이 지적한 위험 구간이 정확히 거기 생긴다 — **두 트랜잭션 사이에 어느 그룹에도
속하지 않은 설비가 DB에 남는다.** 단독키 PK가 만든 제약이라 API 설계로는 피할 수 없다.

**기각한 쪽의 우려는 실재하므로 완화한다.** 응답에 `stolen` 배열을 실어
"이 요청으로 다른 그룹에서 빠진 것과 그 출처 그룹"을 운영자가 보게 한다.
02에서 약속한 그 완화다.

```json
{ "code": "SUCCESS",
  "data": { "members": [ ... ],
            "stolen":  [ { "memberId": "EQP-001", "fromCtrlGrpId": "CG-001" } ] } }
```

### 3. 비활성 그룹의 편성도 저장할 수 있다 — 인질을 풀 길을 막지 않는다

정수장 도메인 관점이 짚은 함정이다. **단독키 PK 때문에 비활성 그룹이 설비를 인질로 잡는다** —
1계열을 `use_yn='N'`으로 내려도 그 펌프는 여전히 `ctrl_eqp_p`에서 1계열 소속이라
2계열에 편성할 수 없다.

그래서 편성 저장 시 **그룹의 `use_yn`을 보지 않는다.** 존재만 확인한다(없으면 404).
비활성 그룹의 편성 화면을 못 열게 막으면 운영자가 빠져나갈 길이 없어진다.

결정 2(뺏어오기)가 이 문제를 대부분 해소하지만, 뺏어오기는 **받는 쪽에서** 하는 조작이다.
주는 쪽에서 먼저 비우고 싶은 경우(빈 배열 저장)를 막지 않는다.

**편성 행 자체는 그룹 비활성화 때 지우지 않는다.** `use_yn='N'`은 "지금 안 쓴다"이지
"편성이 없어졌다"가 아니다. 갈수기/홍수기 계열 전환처럼 껐다 켜는 것이 실제 운전 형태인데,
켤 때마다 다시 편성해야 한다면 운영자는 소프트 삭제를 안 쓰고 그냥 켜둔 채 방치한다.
조회·제어 실행 시점에 상위 그룹의 `use_yn` 필터로 흡수한다.

### 4. 세 테이블 모두 delete-then-insert 한 경로로 구현한다

`ctrl_eqp_p`만 `mdf_*`가 없고 나머지 둘은 있다. 데이터 관점이 **이 비대칭 자체를 결함**으로 봤다 —
구조·의미·수명주기가 같은 편성 테이블인데 감사 정책만 다르면 서비스 계층이 두 코드 경로를 갖게 되고,
그 갈라짐이 코드가 아니라 스키마에서 온다.

해소 방향은 둘(`ctrl_eqp_p`에 `mdf_*` 추가 / 나머지 둘에서 제거)인데 **어느 쪽이든 ERD 수정이 선행**이라
이번 범위가 아니다. 지금은 **셋 다 delete-then-insert 같은 절차**로 구현해 갈라짐을 없앤다.

> **"한 코드 경로"는 과장이었다**(전용 리뷰 지적). 실제로 공유되는 것은 `prepare()`·`indexed()`·`saveFlushing()`뿐이고
> 세 메서드 본문은 거의 동일한 3벌 복제다. 오늘 시점에 셋이 완전히 동일하다는 것은 리뷰가 줄 단위로 확인했으나,
> 그것을 구조적으로 강제하는 장치는 없고 지키는 것은 규율뿐이다. 「알려진 한계」 8에 남긴다.

**대가를 명시한다** — `ctrl_grp_wnp_p`·`ctrl_grp_tag_p`의 `mdf_*`가 **항상 `rgstr_*`와 같아진다.**
`BaseCreatedEntity` javadoc이 말한 *"무의미한 컬럼 두 개"* 가 남은 상태이고, 제약 위반은 아니다.
아래 「알려진 한계」에 남긴다.

**잃는 것과 얻는 것.** 잃는 것은 "이 펌프가 이 그룹에 **처음** 편성된 시각"이다 —
매 저장마다 행이 새로 생기므로 `rgstr_*`는 "마지막으로 이 편성을 만든 사람과 시각"이 된다.
**편성은 상태이지 이력이 아니므로** 그 손실을 받아들인다. 진짜 이력이 필요하면
컬럼 두 개가 아니라 별도 이력 테이블이 답이다(두 컬럼으로는 직전 1회만 남는다).

### 5. 벌크 DELETE는 `@Modifying(flushAutomatically, clearAutomatically)`로만 쓴다

데이터 관점이 세 가지를 짚었고 전부 반영한다.

**(a) 파생 삭제 메서드(`deleteByCtrlGrpId`)를 쓰지 않는다.** Spring Data는 그것을
`SELECT → em.remove() 반복`으로 구현하므로 편성 크기만큼 쿼리가 늘고, 제거된 인스턴스가
영속 컨텍스트에 "삭제 예정"으로 남는다.

> **이 항목은 착수 후 주장을 좁혔다.** 처음에는 데이터 관점을 따라 *"같은 PK로 다시 저장하면
> `ObjectDeletedException`이 나거나 삭제가 취소되고 UPDATE로 바뀐다"* 고 적었으나,
> **파생 삭제 메서드로 바꿔 돌려 보니 14건이 전부 통과했다**(「함정 기록」 1).
> 그래서 근거를 **쿼리 수와 컨텍스트 상태의 단순함**으로만 남긴다.
> 결정 자체는 유지하되 *"이것 없으면 깨진다"* 는 문장을 지웠다.

**(b) 두 옵션을 반드시 함께 켠다.** `clearAutomatically`만 켜면 같은 트랜잭션의 다른 변경이
flush 없이 detach되어 사라지고, `flushAutomatically`만 켜면 1차 캐시가 stale해진다.
하나만 켜면 **조용히 유실되거나 조용히 stale해진다.**

**(c) `@Modifying update`는 쓰지 않는다.** `BaseEntity` javadoc이 직접 금지한 것이다 —
`AuditingEntityListener`를 우회해 `mdf_dttm`이 옛 값에 멈춘다. DELETE는 금지 대상이 아니다
(행이 사라지므로 우회할 리스너가 없다).

### 6. 삭제를 두 번 한다 — 그룹 기준과 ID 기준

replace-all + 뺏어오기를 함께 성립시키려면 삭제가 두 갈래여야 한다.

```
① deleteByCtrlGrpId(대상그룹)   이 그룹의 기존 편성을 비운다 (빠지는 것 처리)
② deleteByIdIn(요청ID들)        다른 그룹에 있던 것을 떼어온다 (뺏어오기)
```

②만 하면 이번 요청에서 **빠진** 설비가 그대로 남는다.

**①만 할 때 무슨 일이 나는지는 착수 후 정정했다.** 처음에는 *"INSERT가 PK 위반으로 터진다"* 고 적었으나
리뷰어가 ②를 제거하고 돌려 **전부 통과시켰다.** 실제로는 assigned-ID라 `merge()`가 남의 그룹 행을 찾아
**`ctrl_grp_id`만 조용히 UPDATE**하고, `rgstr_*`는 `updatable = false`라 옛 그룹에 편성되던 시각에 얼어붙는다.
예외는 나지 않는다.

**즉 ②가 지키는 것은 PK가 아니라 "뺏어온 편성은 새로 만들어진 것"이라는 감사 의미다.**
근거를 고치면서 **그것을 차별하는 테스트도 함께 넣었다**(`뺏어온_편성은_새로_만들어진다`) —
②를 빼면 15건 중 그 하나만 빨간불이 된다(실측).

**`stolen` 목록은 삭제 전에 조회해야 한다** — 지운 뒤에는 어느 그룹에서 왔는지 알 수 없다.

### 7. `sort_ord`는 요청 배열의 순서로 매긴다

`V1__ems_domain.sql`이 *"sort_ord 재정렬을 UPDATE 로 하려면 mdf_* 를 추가해야 한다"* 고 적고
`ctrl_eqp_p`는 그렇게 하지 않았다 — **재정렬 UPDATE를 안 한다는 선언**이다.

replace-all이 이 문제를 소멸시킨다. 목록 순서대로 다시 INSERT하면 재정렬이 UPDATE 없이 끝난다.
따라서 **정렬 전용 엔드포인트를 만들지 않는다**(02에서도 같은 결정).
`sortOrd`는 1부터 배열 순서대로 부여하며 NULL을 넣지 않는다 —
02의 마스터 2종과 달리 여기서는 순서가 요청이 정하는 값이라 "미지정"이라는 상태가 없다.

### 8. 응답 타입을 세 자원이 공유한다 — 필드명은 `memberId`다

세 편성 테이블이 구조적으로 동일하므로(대상ID + `sort_ord` + 감사) 응답 record를 하나로 쓴다.
`CtrlGrpMemberResponse(memberId, sortOrd, rgstrDttm, rgstrId)`.

**요청은 자원별로 나눈다** — `eqpIds`/`wnpIds`/`tagSns`. 보내는 쪽이 무엇을 보내는지가
필드명으로 드러나야 하고, 이건 프론트가 직접 조립하는 값이다.

**대가**: 응답의 식별자 필드가 `eqpId`가 아니라 `memberId`다. 자원별로 쪼개면
record가 3벌 더 늘고 셋이 필드명만 다른 쌍둥이가 된다. 세 편성 화면이 같은 컴포넌트를 쓸 수 있다는
이점이 더 크다고 봤다. OpenAPI 스키마 이름은 유일하므로 02가 경계한 충돌 문제는 없다.

### 9. 편성 명세는 `ctrl` 도메인이 소유한다

`apps/CLAUDE.md`의 교차 도메인 소유 규칙 ①("그 관계를 만들고 끊는 API를 소유하는 도메인에 둔다")로
셋 다 `ctrl`이다 — "제어그룹에 설비/지점/태그를 **편성한다**"이기 때문이다.

**`ctrl_grp_wnp_p`에 규칙 ②를 적용하지 않는다.** PK가 `wnp_id` 단독이라 ②로 재면 `wnp`가 되지만,
**①에서 이미 갈리므로 ②까지 가지 않는다.** ①이 먼저다.

따라서 `wnp` 도메인 패키지는 이번에 변경이 없다. 편성 API가 `wnpId`를 다루지만 `String` 스칼라이므로
도메인 간 타입 참조가 생기지 않는다.

## 구현 상세

### 저장 절차 네 단계

```
① 그룹 존재 확인 + 요청 안 중복 검사
② stolen 조회        ← 삭제 전에 해야 "어느 그룹에서 왔는지"를 알 수 있다
③ 삭제 두 갈래       ← 그룹 기준(빠지는 것) + ID 기준(뺏어오는 것)
④ INSERT + flush     ← 배열 순서로 sort_ord를 1부터, 감사 컬럼을 채운 뒤 응답
```

②를 ③보다 먼저 두는 것이 `stolen` 보고의 전제다. 지운 뒤에는 출처 그룹을 알 방법이 없다.

③이 두 갈래인 이유 — ①만 하면 뺏어오려는 설비가 남의 그룹에 남아 INSERT가 PK 위반으로 터지고,
②만 하면 이번 요청에서 **빠진** 설비가 그대로 남는다.

④의 `flush()`는 02 「함정 기록」 5와 같은 이유다. 감사 컬럼은 flush 시점에 채워지므로
그 전에 응답을 만들면 `rgstrDttm`이 비어 나간다.

### 세 자원이 한 코드 경로를 타는 방식

`indexed(memberIds, factory)` 하나가 배열 순서를 1부터의 `sortOrd`로 바꿔 세 엔티티를 만든다.
스키마의 감사 컬럼 비대칭(`ctrl_eqp_p`만 `mdf_*` 없음)이 서비스 계층까지 번지지 않게 하는 장치다.

## 함정 기록

1. **"delete-then-insert는 flush 경계가 없으면 PK 충돌이 난다"는 전제가 이 경로에서는 성립하지 않았다.**

   문서 02가 이것을 마지막 미증명 위험으로 지목했고, 이번 구현은 벌크 DELETE에
   `@Modifying(flushAutomatically, clearAutomatically)`를 걸어 대비했다.
   **그런데 그 대비가 정말 필요한지 확인하려고 파생 삭제 메서드로 바꿔 돌려 보니 14건이 전부 통과했다.**

   추정되는 이유는 02가 "결함"으로 지목했던 바로 그 경로다 — assigned-ID라 `save()`가 `merge()`를 타고,
   `merge`의 존재 확인 SELECT가 보류 중이던 DELETE를 함께 flush시킨다.
   **02가 잠복 결함으로 본 merge 경로가 여기서는 안전판 노릇을 하는 셈이다.**
   다만 이 설명은 **추정이며 실행으로 확인하지 않았다** — SQL 문 순서를 뽑아 대조하지 않았다.

   **그래서 주장을 좁혔다.** 벌크 DELETE를 유지하되 근거를 "쿼리 수와 컨텍스트 상태의 단순함"으로 바꾸고,
   코드 주석과 이 문서에서 *"이것 없으면 깨진다"* 는 문장을 지웠다.
   **검증하지 못한 근거를 코드 주석에 남기면 다음 사람이 그것을 사실로 읽는다.**

2. **교체 응답을 배열로 착각해 테스트가 깨졌다.** 조회는 배열(`data`)이고 교체는 객체(`data.members`)인데
   `세_자원이_같은_규칙이다`에서 교체 응답에 배열용 헬퍼를 그대로 썼다.
   첫 빌드의 유일한 실패였고 **코드가 아니라 단언이 틀린 경우**다.
   같은 실수가 남았는지 `grep -n "memberIds(data("`로 전수 확인했다 — 나머지 넷은 전부 `GET`이라 옳았다.

3. **`MemberFactory`를 `Function`의 하위 타입으로 만들 뻔했다.** 두 인자를 받아야 하는데 `Function`을
   상속해 `apply`를 `UnsupportedOperationException`으로 막는 형태를 처음에 썼다.
   **계약을 상속해 놓고 그 계약을 거부하는 타입**이라 잘못된 설계다. 독립 인터페이스로 바꿨다.

### 리뷰에서 나와 고친 것

4. **「결정 6」②의 근거가 틀렸다.** [전용 리뷰 — 중간]
   *"①만 하면 INSERT가 PK 위반으로 터진다"* 고 적었는데 리뷰어가 ②를 제거하고 돌려 **전부 통과**시켰다.
   실제 동작은 merge에 의한 조용한 UPDATE이고, ②가 지키는 것은 PK가 아니라 감사 의미다.

   **함정 1과 똑같은 유형의 오류를 바로 옆 결정에서 반복한 것**이다 — 벌크 DELETE에 대해 "이것 없으면 깨진다"를
   철회해 놓고, 같은 문단의 ②에 대해서는 같은 형태의 미검증 단정을 그대로 뒀다.
   이번에는 근거만 고치지 않고 **차별하는 테스트를 함께 넣었다**: ②를 빼면 그 테스트 하나만 빨간불이 된다.

5. **철회했다는 주장이 테스트 파일에 5곳 살아 있었다.** [전용 리뷰 — 높음]
   함정 1에 *"코드 주석과 이 문서에서 그 문장을 지웠다"* 고 적었으나 **테스트 파일은 손대지 않았다.**
   그중 하나는 `@DisplayName`의 *"…벌크 DELETE가 UPDATE로 뒤바뀌지 않았다는 **증거**"* 로,
   **테스트 리포트에 그대로 출력되는 문자열**이라 가장 눈에 띄는 자리에서 거짓 근거를 주장하고 있었다.
   클래스 javadoc·주석 4곳과 함께 정정했다.
   **교훈: 주장을 철회할 때 그 주장이 복제된 자리를 전부 세어야 한다.** 문서·코드 주석·테스트 이름은 각각 다른 파일이다.

6. **요청 배열 원소에 형식 검증이 없었다.** [양쪽 리뷰 — 중간]
   리스트에 `@NotNull`만 걸고 원소에는 아무 제약이 없어, 실측 결과
   `[null]`·37자 초과는 **500 + ERROR 로그**, `["   "]`는 **200으로 공백 PK가 저장**됐다.
   02가 `CtrlGrpAddRequest`에서 지킨 규약을 편성 요청에서 빠뜨린 것이고,
   이번에 `ColLength.EQP_ID`·`TAG_SN`을 추가해 놓고 **`@Column(length=)`에만 쓰고 검증에는 안 썼다.**
   `List<@NotBlank @Size(max = …) String>`으로 고쳤다.

7. **편성 저장에 409 번역이 없었다.** [/code-review — 중간]
   02의 `CtrlGrpService.saveFlushing`은 `DataIntegrityViolationException`을 `EMS-409`로 되던지고
   그 javadoc에 *"설계 전체가 409를 약속하고 있으므로 그 약속을 경합 상황에서도 지킨다"* 고 적어 뒀는데,
   **편성 서비스의 세 저장 경로에는 그 번역을 붙이지 않았다.**
   미편성 설비를 두 그룹이 동시에 가져가면 양쪽 삭제가 0행을 지우고 둘 다 INSERT해 뒤엣것이 500이 된다.
   세 곳이 같은 헬퍼(`saveFlushing`)를 쓰도록 묶어 고쳤다 — 3벌 복제를 한 줄 줄인 효과도 있다.

8. **공허 참 2건.** [전용 리뷰 — 중간]
   `assertThat(data.path("members")).isEmpty()`와 `...path("stolen")).isEmpty()`가 그것이다.
   리뷰어가 record 컴포넌트명을 바꿔 **JSON 필드를 통째로 없앤 뒤** 실행해 확정했다 —
   `path()`는 키가 없으면 `MissingNode`를 돌려주고 AssertJ가 그것도 "비어 있음"으로 본다.
   **02가 이 함정을 알고 `isArray()` 가드를 넣었는데 03에서 빠졌다** — 같은 사람이 같은 리포에서
   두 문서 사이에 규율을 흘린 것이다. 가드를 넣었다.

9. **`ems-service/CLAUDE.md`가 이번 변경으로 거짓이 됐는데 "변경 없음"이라고 적었다.** [전용 리뷰 — 중간]
   그 파일이 *"편성 명세 3종에는 아직 엔티티가 없다"* 라고 말하고 있었고,
   문서 03의 「변경 내역」은 *"02가 세운 문장을 거짓으로 만들지 않는다"* 고 주장했다. **그 주장 자체가 틀렸다.**
   02는 같은 자리에서 정확히 이 갱신을 했는데(「변경 내역」에 기록돼 있다) 03에서 놓쳤다.
   현재 상태 절을 다시 쓰고, master 존재 확인 "계약"이 아직 구현되지 않았다는 사실도 그 파일에 명시했다.

10. **테스트 격리의 근거 주석이 거짓이 됐다.** [전용 리뷰]
    `CtrlGrpSliceIntegrationTest`가 *"`ctrl_grp_m`은 이 클래스만 쓰므로"* 라고 적은 채 그 테이블을 통째로 비우는데,
    이번에 편성 테스트가 같은 테이블을 쓰기 시작했다. **실제 피해는 없다** — 클래스가 순차 실행되고
    양쪽 다 `@BeforeEach`에서 자기 픽스처를 다시 세운다. 다만 그 주석이 근거로 남아 있으면
    다음 사람이 병렬 실행을 켜거나 `@BeforeAll`로 옮길 때 무너진다. 실제 안전 근거로 바꿔 적었다.

## 알려진 한계

1. **master 키 존재 확인이 **여전히 없다**.** [01](01-제어그룹-도메인-DDL.md) 「한계 4」·[02](02-제어그룹-마스터-CRUD.md) 「한계 1」을 승계한다.
   **이번 작업이 그 위험을 실제로 열었다** — 01·02 시점에는 편성 행을 만들 경로 자체가 없었으나
   이제 있다. `PUT .../eqp`에 존재하지 않는 `eqpId`를 넣어도 그대로 저장되고, 단독키 PK라
   중복 충돌조차 나지 않는다. 터지는 곳은 **제어 실행 시점**이다.
   현재 그물은 화면이 master 목록에서 고른 값만 보낸다는 전제 하나뿐이고, 그건 약한 그물이다.

2. **➖ 검증불가 — 벌크 DELETE의 필요성.** 「함정 기록」 1. 파생 삭제 메서드로도 통과하므로
   현재 구현이 정확성에 필수라는 것은 확인되지 않았다. SQL 문 순서를 뽑아 대조하면 판정된다.

3. **replace-all은 last-write-wins다.** 두 운영자가 같은 그룹의 편성을 동시에 저장하면 나중 요청이 이긴다.
   `@Version`이 리포 전체에 0건이고 이번에 도입하지 않았다.
   **뺏어오기와 겹치면 더 조용하다** — A가 EQP-1을 넣는 사이 B가 같은 설비를 가져가면
   A의 응답은 성공이고 `stolen`도 비어 있는데 실제 소속은 B다.

4. **`ctrl_grp_wnp_p`·`ctrl_grp_tag_p`의 `mdf_*`가 영원히 `rgstr_*`와 같다.** 「결정 4」가 감수한 대가다.
   `BaseCreatedEntity` javadoc이 말한 *"무의미한 컬럼 두 개"* 가 남은 상태이고 제약 위반은 아니다.
   해소하려면 ERD를 먼저 고쳐 세 편성 테이블의 감사 정책을 맞춰야 한다.

5. **`rgstr_*`가 "최초 편성"이 아니라 "마지막 저장"이다.** delete-then-insert의 귀결이다.
   편성 화면에서 아무것도 안 바꾸고 저장만 눌러도 전 행의 등록 시각이 갱신된다.
   **편성은 상태이지 이력이라는 전제**에서 받아들인 것이고, 진짜 이력이 필요하면 별도 테이블이 답이다.

6. **➖ 검증불가 — 컨테이너 E2E·게이트웨이 경유·OpenAPI 스펙.** 02의 한계 2·3·4를 그대로 승계한다.

7. **세 자원의 구현이 구조적으로 강제되지 않는다.** 「결정 4」의 *"한 코드 경로"* 는 과장이고
   실제로는 3벌 복제다(공유되는 것은 `prepare()`·`indexed()`·`saveFlushing()`).
   오늘 시점에 셋이 완전히 동일한 것은 리뷰가 줄 단위로 확인했으나, 한쪽만 고쳐지는 것을 막는 장치는 없다.

8. **wnp·tag는 eqp보다 얇게 검증된다.** `세_자원이_같은_규칙이다`가 밟는 것은
   겹치는 재저장·뺏어오기 2종뿐이고, `sort_ord` DB값·빈 배열·404·중복 409·감사 컬럼은 eqp에서만 본다.
   세 구현이 동일하다는 전제에 기대고 있으며, 그 전제를 강제하는 장치가 위 7번대로 없다.

9. **단정형으로 남았으나 검증하지 않은 주장이 둘 있다.**
   「결정 5(b)」의 *"하나만 켜면 조용히 유실되거나 조용히 stale해진다"* 는 한쪽만 켠 상태를 시험한 적이 없다.
   `requireNoDuplicateWithin`의 *"중복을 그대로 두면 제약 위반으로 500이 난다"* 도 같다 —
   같은 merge 경로라면 두 번째가 첫 번째를 덮어써 예외 없이 끝날 가능성이 있다.
   **409 가드 자체는 정렬순서가 둘 중 어느 쪽으로 정해지는지 모호하다는 이유로 옳다.**

10. **한 번, `--rerun-tasks` 없는 실행에서 전 HTTP 호출이 이전 컨테이너 포트로 `Connection refused`가 났다.**
    리뷰어가 관찰했고 재실행하니 정상이었다. 원인을 특정하지 못했다.
    **상태를 단언하지 않는 테스트였다면 죽은 DB 위에서도 통과했을 상황**이라 남긴다.

11. **편성 대상의 개수 상한이 없다.** `eqpIds`에 수만 건을 넣으면 그만큼 INSERT가 나간다.
   `@Size(max=)`를 걸지 않았다 — 운영상 상한이 확정되지 않았고, 임의로 정하면 그 숫자가 근거 없이 굳는다.
