## 발단

[01](01-필터-체인과-요청-처리-순서.md)이 필터 체인을 문서화하면서 **라우트 접두사에 묶인 값들이 서로 어긋나 있다**는 것을 함께 드러냈다. `ApiDocsRouteConsistencyTest`가 5건 중 4건 실패 상태였고, 그 실패가 CI에 잡히지 않고 있었다.

원인은 규약이 두 번 뒤집힌 것이다.

| 시점 | 커밋 | 경로 규약 | 함께 바뀐 것 |
|---|---|---|---|
| 2026-08-21 | step-18 | **서비스명 접두** `/{서비스명}/**` | 전부 (yml·테스트·CLAUDE.md·아키텍처 문서) |
| 2026-08-25 | `6bb365d` | API prefix `/api/{prefix}/**` | **13개 파일**(`--stat`). 경로 규약에 직접 묶인 것 8개 — gateway CLAUDE.md·yml·테스트 2종, realtime CLAUDE.md·`TelemetryStreamController`, compose 2종 |
| 2026-08-25 | `f76abf9` | **서비스명 접두**로 복귀 | yml의 routes·swagger-urls·permit-all-paths **만** |

`f76abf9`가 되돌린 범위가 yml 안쪽에 그쳐, 바깥 넷(`ticket-auth-paths`·테스트 2종·CLAUDE.md·compose 2종)이 API prefix 방식에 남았다.

**`6bb365d`의 커밋 메시지는 "feat: docker-compose-dev.yml kafka"다.** 경로 규약을 뒤집으면서 13개 파일을 함께 바꿨는데 그 사실이 메시지에도 문서에도 없다. 그래서 `f76abf9`를 작성한 사람이 "여기 규약이 바뀌었다"는 것을 알 방법이 없었고, 되돌릴 범위도 알 수 없었다. **결정 이력이 없는 결정은 부분적으로만 되돌려진다.**

### 왜 지금까지 드러나지 않았는가 — 은폐 두 겹

| 층 | 내용 |
|---|---|
| 기본값 | `swtp.auth.mode`가 `none`이라 티켓 경로·JWKS를 아예 타지 않는다. **인증을 켜는 정수장에서만** 발화한다 |
| CI | `Jenkinsfile`이 `gradlew --version` → `master-service:sonar` → `bootJar` → `compose up` 순서다. **`test`를 돌리지 않는다** — `bootJar`는 `test`에 의존하지 않는다 |

`infrastructure/docs/03`이 *"실패 방향이 fail-closed에서 fail-open으로 뒤집힌다"* 로 감수했던 위험이 한 걸음 더 나간 형태다. 무인증으로는 정상 동작하는데 인증을 켜는 순간 전면 503이 된다 — **보안을 강화하는 행위가 장애를 부르므로 발견 시점이 가장 나쁜 때(운영 전환 직전)로 밀린다.**

### `docs/03`이 고쳤다고 기록한 지점 하나가 실제로는 안 고쳐져 있었다

`infrastructure/docs/03`의 「바꾼 곳 — **다섯** 지점」 표는 `apps/gateway/src/main/resources/application.yml`을 포함하고, *"계획 단계에서 넷으로 셌으나 게이트웨이 자기 yml이 하나 더 있었다"* 라고까지 적었다. 그런데 그 커밋(`2973d8f`)은 **그 파일을 건드리지 않았다.** `6bb365d^`부터 HEAD까지 줄곧 `${SWTP_AUTH_MODE:internal}`이다.

드러나지 않은 이유가 그 문서의 검증 설계에 있다. 실측 (A)(B)가 **전부 컨테이너**에서 이뤄졌는데, 컨테이너에서는 config-server가 내려주는 `none`이 앱 자기 yml을 이긴다. 게이트웨이 yml의 `internal`이 표면화되는 곳은 **config-server 없이 뜨는 로컬 단독 기동**뿐이고, 그건 실측 대상이 아니었다.

## 결정 (2026-09-09)

### 1. 경로 규약은 서비스명 접두 방식(`/{서비스명}/**` + `RewritePath`) 하나다

step-18의 결정을 그대로 유지한다. 뒤집혔던 것을 되돌리는 것이 아니라, **뒤집은 쪽에 근거 기록이 없으므로 근거가 있는 쪽을 남긴다.**

**명칭 주의**: step-18은 `/api/{prefix}/**`를 *구방식*, `/{서비스명}/**`를 *신방식*이라 부른다. 최근 커밋 순서로 보면 반대로 읽히므로 이 문서는 **서비스명 접두 방식 / API prefix 방식**이라는 중립 명칭을 쓴다.

이 규약을 남기는 실질적 근거는 step-18 함정 #2다. API prefix 방식은 `Path` 술어가 **세그먼트 단위**로 매칭하므로 `Path=/api/job/**`가 `/api/jobs`에 도달하지 못한다 — 아키텍처 8.2가 설계한 Job REST API(`GET /api/jobs`, `GET /api/job-executions/{id}`)가 게이트웨이 경유로 전부 404다. **규약 정리이자 잠재 결함 제거다.**

**기각한 대안 — API prefix 방식으로 통일.** 스웨거에 표시되는 경로와 실제 호출 경로가 같아진다는 이점이 있으나(「알려진 한계」 1), 위 세그먼트 매칭 제약과 "라우트가 서비스의 경로 작명을 구속한다"는 문제를 되살린다. 그 이점은 OpenAPI `servers` 설정으로도 얻을 수 있다.

목표 상태가 `6bb365d^`에 그대로 남아 있고 테스트 2종은 그 이후 아무도 건드리지 않았으므로, **추측이 아니라 이력에서 복원**했다.

### 2. 인증 기본값은 `none` — 게이트웨이 yml이 유일한 미착지였다

`docs/03`이 정한 다섯 지점 중 넷은 이미 `none`이다. 게이트웨이 yml 한 줄만 `internal`로 남아 있었고, 그것을 `none`으로 맞춘다.

이 한 줄이 만들던 실제 갈라짐: config-server가 붙으면 `config-repo`의 `none`이 이기지만, **게이트웨이를 `bootRun`으로 단독 기동하면** 자기 yml의 `internal`이 살아나고 JWKS 기본값이 `localhost:8085`라 auth-service까지 띄워야 했다. `docs/03`이 master-service에서 없앤 것과 같은 종류의 로컬↔컨테이너 갈라짐이다.

### 3. `compose-dev`의 인증 두 줄을 환경변수 형태로 올린다

`compose-dev.yaml`은 `SWTP_AUTH_MODE: none`과 JWKS URL을 **리터럴**로 박고 있었다. `.env`가 닿지 않으므로 이 파일로 배포하는 개발서버는 **인증 모드를 한 번도 태워 보지 못한다.** `docs/03` 「남은 것」 2번이 *"기본값을 다시 뒤집을 때 함께 볼 자리"* 로 예고한 지점이 이번에 현실이 됐다.

`${SWTP_AUTH_MODE:-none}` / `${SWTP_AUTH_JWKS_URI:-...}` 형태로 올려 "정수장별 차이는 환경변수 한 줄" 규약이 dev에서만 깨진 상태를 함께 닫는다.

### 4. actuator 노출 축소는 이번 범위에서 뺀다

운영·관측 검토가 찾은 것 — `config-repo/application.yml`의 `management.endpoints.web.exposure.include`가 `health`·`env`·`busrefresh`·`prometheus`·`mappings` 5종이고 `permit-all-paths`의 `/*-service/actuator/**`가 이를 무인증으로 연다. **외부에서 `POST /{서비스명}/actuator/busrefresh` 한 줄로 전 정수장 설정 리프레시를 유발할 수 있다.**

이번에 넣지 않는 이유는 셋이다. 화이트리스트를 좁히면 `smoke-test.ps1`을 함께 고쳐야 하고(그 스크립트가 스스로 그 계약을 적어 뒀다), `mode=none` 사이트에서는 화이트리스트에서 빼도 어차피 전부 열려 있어 **본질적으로 방화벽 과제**이며, 무게중심이 `infrastructure/`로 넘어간다. 「다음 단계」에 심각도와 함께 남긴다.

### 갈린 의견 — SSE를 완료 조건에서 빼라는 지적을 기각했다

운영·관측 검토는 *"`ticket-auth-paths`를 고쳐도 다운스트림 `swtp-security-starter`가 Bearer를 요구하고 realtime-service가 ticket 파라미터를 읽지 않으므로 SSE는 통과할 수 없다"* 며 완료 조건에서 제외를 권고했다.

**전제가 사실과 다르다.** `apps/realtime-service/build.gradle`에 `swtp-security-starter`가 없다. 그 앱의 CLAUDE.md가 이유를 적어 뒀다 — *"브라우저 `EventSource`/`WebSocket`이 핸드셰이크에 헤더를 붙일 수 없어서 그 방식이 성립하지 않는다. 대신 게이트웨이가 쿼리 파라미터의 단기 ws-ticket을 검증한다."* realtime-service는 **게이트웨이가 유일한 인증 경계**이므로 티켓 검증이 게이트웨이에서 끝나고, 다운스트림은 재검증하지 않는다. ticket 파라미터를 읽을 코드가 없는 것도 정상이다.

따라서 `ticket-auth-paths` 수정만으로 종단간 성립하며, SSE 핸드셰이크를 완료 조건에 유지한다. step-18의 「운영 확인 지점」도 같은 항목을 두고 있다.

## 구현 상세

### 경로가 갈리는 지점

```text
브라우저            /realtime-service/api/realtime/telemetry/stream?ticket=<티켓>
                          │
                    [게이트웨이]
                    RequestId(MIN) → AccessLog(+10) → JwtAuth(+20)
                          │                              ↑
                          │        ticket-auth-paths 는 여기서 판정된다
                          │        = RewritePath 이전의 외부 경로
                          │        그래서 /realtime-service/** 여야 한다
                    RewritePath (라우트 필터, order 1)
                          │  /realtime-service 를 벗긴다
                          ▼
realtime-service    /api/realtime/telemetry/stream
```

### JWKS가 게이트웨이 자기 라우트를 경유하는 이유

```text
gateway ──(1) JWKS 조회──► gateway:8080/auth-service/api/auth/.well-known/jwks.json
                                  │
                                  │ (2) permit-all 통과 → RewritePath → lb://auth-service
                                  ▼
                            auth-service (server.port=0)
```

`micro` 프로파일이 `server.port: 0`을 주므로 auth-service의 컨테이너 안 실제 포트는 매 기동 달라진다 — 직접 주소를 박을 수 없다. 컨테이너끼리는 Eureka로 찾지만 **JWKS 조회는 그 경로를 쓸 수 없다**(`NimbusReactiveJwtDecoder`가 평범한 HTTP URI로 가져온다). 그래서 게이트웨이를 경유하고, **그 순간 이 URL이 라우트 접두사에 묶인다.** 이번 회귀의 3번이 정확히 이 결합이다.

기동 순서상 순환은 없다 — JWKS 조회는 빈 생성 시점이 아니라 **첫 토큰 검증 시점**에 일어난다. 그래서 기동은 성공하고 첫 요청에서 깨진다. 게이트웨이 healthcheck에 JWKS 조회를 넣지 않는 이유이기도 하다(자기 자신을 경유하는 헬스체크가 되어 기동 판정에 순환이 생긴다).

## 함정 기록

1. **`git checkout <rev> -- <path>`는 스테이징까지 한다.** 복원 직후 `git diff`가 비어 보여 "복원이 안 됐나" 오판하기 쉽다. `git diff --cached`로 봐야 한다.
2. **`ApiDocsRouteConsistencyTest`가 이미 빨간불이면 새 실패를 숨긴다.** 4건이 깨진 채 방치돼 있어서, 그 기간에 생긴 다른 불일치는 같은 빨간불에 섞여 구분되지 않았다. 이미 실패하는 테스트는 그물이 아니다.
3. **화이트리스트에서 게이트웨이 **자기** 경로와 **서비스** 경로를 구분해야 한다.** `f76abf9`가 `/swagger-ui/**`(게이트웨이 자기 집계 UI)를 `/*-service/swagger-ui/**`로 바꿔 놓았는데, 이건 라우팅으로 끌어오는 대상이 아니라 게이트웨이가 직접 호스팅하는 경로다. 접두사를 붙이면 영영 매칭되지 않는다.
4. **값이 복제된 곳을 grep으로 세고 시작한다.** JWKS URL은 5개 파일에 있었다(compose 2종·`.env.example`·결정 이력 2종). 설정 3곳만 고치고 `.env.example`을 두면 문서가 옛 URL을 계속 가르친다.

### 리뷰에서 나와 고친 것

5. **이력에서 복원한 것이 곧 완성은 아니다.** `6bb365d^`의 `JwtAuthGlobalFilterTest`는 `ticketAuthPaths`만 운영 형태였고 `permitAllPaths`는 `/api/auth/login`인 채였다 — step-18이 *"운영 설정과 형태 일치"* 를 근거로 적어 두고 절반만 적용한 상태다. 복원 결과를 그대로 두면 **화이트리스트 픽스처가 운영과 다른 상태가 유지된다.** 이번에 함께 맞췄다. 「변경 내역」이 처음에 이걸 "복원했다"고 적어 사실보다 앞서 있었다.
6. **뒤집은 커밋의 `--stat` 전체를 복원 체크리스트로 써야 한다.** 착수 시 `6bb365d`가 바꾼 범위를
   "yml·테스트 2종·CLAUDE.md·compose 2종"으로 **기억에 의존해 셌고**, 실제로는 13개(경로 규약 관련
   8개)였다. 그 한 번의 누락이 `TelemetryStreamController`의 Javadoc을 남겼다. **자기 문서의
   「함정 기록」 4가 "값이 복제된 곳을 grep으로 세고 시작한다"였는데, 정작 커밋 쪽은 세지 않았다.**
7. **실측 블록에 손질한 요약을 넣었다 — 이번 작업에서 가장 나쁜 실패다.** 「실측 결과」 3)에
   `git grep 'gateway:8080/api/auth' -- ':!docs'` → `(없음)`을 붙였는데 **그 명령을 실행한 적이 없다.**
   실제로 돌린 것은 `-- ':!docs/seminar'`였고 결과도 2건이었다. 게다가 `':!docs'`는 루트 `docs/`만
   제외해 `apps/*/docs`·`infrastructure/docs`가 남으므로 **그 출력은 어느 시점에도 나올 수 없다.**
   결론(설정·코드에 옛 URL 0건)은 참이었지만, 실측 블록에 재현 불가능한 출력이 들어가면 같은 블록의
   나머지 수치까지 신뢰를 잃는다. 전용 리뷰어가 직접 명령을 돌려 잡았다 — **개발한 에이전트가 자기
   검증을 채점하면 이 종류는 걸리지 않는다.**
8. **규약을 근거로 삼는 코드 주석이 스타터에도 있었다.** `SwtpOpenApiEnvironmentPostProcessor`의 Javadoc이 *"라우트는 `Path=/api/{prefix}/**`이고 StripPrefix가 없다"* 를 문서 경로 주입의 근거로 적고 있었다. 주입 값은 지금도 맞지만 근거가 반대라, 그 문장을 믿고 주입을 걷어내면 8개 서비스 스펙이 조용히 404가 된다. 「접두사에 묶인 값」 목록을 만들 때 **설정 파일만 세고 코드 주석을 빠뜨렸다.**

## 알려진 한계

1. **스웨거에 표시되는 경로와 실제 호출 경로가 갈린다.** `SwtpOpenApiAutoConfiguration`이 `servers`를 `"/"`(현재 오리진)로 고정하는데, 이 규약에서는 게이트웨이 경유 시 앞에 `/{서비스명}`이 더 붙어야 한다. 즉 **swagger-ui의 "Try it out"이 게이트웨이 경유에서 404**가 된다(서비스 직접 접근은 정상). 그 코드의 주석 *"게이트웨이 경유(:8080)와 서비스 직접 접근(:8081) 양쪽에서 모두 올바르게 동작한다"* 는 API prefix 방식 전제의 문장이라 지금은 성립하지 않는다.
   `servers`에 `"/"`와 `"/{서비스명}"` 둘을 등록하면 swagger-ui가 드롭다운을 주므로 해결 가능하나, `swtp-web-starter` 변경이라 11개 앱에 걸린다 — 별건이다(「다음 단계」).
2. **컨테이너 실측은 완료했다(2026-09-09).** 다만 `--profile elk`·`ai`는 띄우지 않았고, 부하·다중 노드도 대상이 아니다. 확인한 것은 인증 경로와 라우팅 정합성뿐이다.
3. **actuator 5종 무인증 노출이 남는다.** 「결정」 4 참조. `busrefresh`가 특히 위험하다.
4. **`Jenkinsfile`이 이 변경을 검증하지 못한다.** `test`를 돌리지 않고, `smoke-test.ps1`·`deploy-core.ps1`을 호출하지 않으며, `compose-dev`로 배포하는데 그 스택은 `mode=internal`을 태우지 않는다. 「결정」 3으로 태울 **수단**은 생겼으나 파이프라인이 태우지는 않는다.
5. **결정 이력 문서 2곳에 옛 JWKS URL이 남는다** — `docs/scaffold/steps/step-10`(동결)과 `infrastructure/docs/03`(완료). 그 시점의 기록이라 소급 수정하지 않는다(step-18의 같은 판단을 따른다). 다만 `docs/03`은 「바꾼 곳」 표에 실제로 안 바뀐 지점을 포함하고 있어, 그 표를 근거로 삼을 때 주의가 필요하다.
6. **`ticket-auth-paths`가 서비스 전체(`/realtime-service/**`)를 연다.** step-18이 정한 값을 그대로
   복원했고 realtime-service가 현재 스트림 엔드포인트 하나뿐이라 지금은 문제가 없다. 다만 바로 위
   주석은 *"실시간 스트림으로만 좁힌다"* 이고, 이 서비스는 `swtp-security-starter`를 쓰지 않아
   **게이트웨이가 유일한 인증 경계**다. 여기에 REST 엔드포인트가 하나라도 생기면 30초짜리
   ws-ticket을 쿼리 파라미터로 붙여 그 엔드포인트까지 호출할 수 있다.
   덧붙여 `AccessLogGlobalFilter`의 `gateway.target`은 **쿼리스트링을 포함한 전체 URI**를 남기므로
   접근 로그에 티켓이 실린다 — ws-ticket을 따로 만든 이유가 "장수명 토큰을 로그에 남기지 않으려는
   것"이었으니 수명이 짧을 뿐 같은 성질의 노출이다. 리뷰 지적이고, 좁히는 것은 step-18의 결정을
   바꾸는 일이라 이번 범위에서 하지 않았다(「다음 단계」).
