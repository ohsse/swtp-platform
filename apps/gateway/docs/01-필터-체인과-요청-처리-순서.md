## 발단

게이트웨이는 플랫폼의 유일한 외부 진입점이고, 요청 1건이 여기서 자체 필터 3종과 프레임워크
내장 필터 4종을 순서대로 통과한다. 그런데 그 순서와 각 필터의 계약이 **네 곳에 흩어져 있었다** —
각 클래스의 Javadoc, `apps/gateway/CLAUDE.md`의 순서표 3행, `application.yml` 주석, 동결된
`docs/scaffold/steps/step-18`. 어느 것도 *"사용자 요청이 들어와서 응답이 나갈 때까지"* 를 한 번에
보여주지 않는다.

흩어져 있는 것 자체보다, 그 때문에 **회귀가 조용히 성립한다는 것**이 문제다.
`JwtAuthGlobalFilter`는 경로 화이트리스트를 `RewritePath` **이전**의 외부 경로로 판정하는데,
이 사실이 CLAUDE.md 한 줄로만 남아 있어 라우트를 고칠 때마다 재발견 대상이 된다.
실제로 그 재발이 일어났고, 전말은 [02](02-경로-규약-확정과-인증-기본값-정렬.md)에 있다.

이 문서는 그 한 벌을 만든다. **코드는 바꾸지 않는다.**

## 큰 그림

```text
  브라우저 / 외부 클라이언트
        │  GET /master-service/api/master/tags
        │  Authorization: Bearer <access token>
        ▼
  ┌──────────────────────────────────────────────────────────┐
  │ gateway :8080   ─   Netty · WebFlux (서블릿 스택 아님)     │
  └──────────────────────────────────────────────────────────┘
        │
        ├─① CORS 처리       globalcors ─ 필터 체인보다 앞
        │
        ├─② 라우트 매칭     Path 술어 ──✗──► 404 (필터 체인을 타지 않는다)
        │
        ├─③ GlobalFilter 체인 (order 오름차순)
        │      RequestId   HIGHEST      X-Request-Id 발급·전파
        │      AccessLog   HIGHEST+10   시작 시각만 잡고 통과
        │      JwtAuth     HIGHEST+20   토큰 검증 ──✗──► 401 · 503
        │
        ├─④ 라우트 필터     RewritePath ─ 외부 경로 → 서비스 경로
        │
        └─⑤ 내장 라우팅     lb://master-service → 인스턴스 주소
                                       ──✗──► 503 (인스턴스 없음)
        │
        ▼
  업무 서비스 (서블릿)  ─  X-Request-Id · X-User-Id · X-User-Roles 를 받는다
```

**②가 ③보다 앞이라는 것이 이 그림에서 가장 자주 오해되는 자리다.** 라우트 매칭은
`RoutePredicateHandlerMapping`이 하고, 그것이 매칭에 성공했을 때 돌려주는 핸들러가 필터 체인을
돌리는 `FilteringWebHandler`다. 즉 **매칭이 먼저이고 필터가 나중**이라, 어떤 술어에도 걸리지
않은 요청은 GlobalFilter 셋을 아예 타지 않는다. 접근 로그도 `X-Request-Id`도 남지 않는다.

그리고 ③이 ④보다 앞이라는 것이 화이트리스트 규칙의 근거다. 인증 판정 시점에 경로는 아직
클라이언트가 보낸 그대로이므로, **화이트리스트와 티켓 경로는 리라이트 이전의 외부 경로로 쓴다.**

## 필터 순서표

체인은 GlobalFilter와 라우트 필터를 한 줄로 합쳐 `order` 오름차순으로 정렬한 결과다.
자체 필터가 `HIGHEST_PRECEDENCE`(= `Integer.MIN_VALUE`) 근처를 쓰므로 **항상 앞을 차지한다.**

| order | 필터 | 소속 | 하는 일 |
|---|---|---|---|
| `MIN` | `RequestIdGlobalFilter` | 자체 | `X-Request-Id` 발급·전파 |
| `MIN+10` | `AccessLogGlobalFilter` | 자체 | 접근 로그 (기록은 종료 시점) |
| `MIN+20` | `JwtAuthGlobalFilter` | 자체 | 토큰 검증 · 사용자 헤더 주입 · 위조 헤더 제거 |
| `-1` | `NettyWriteResponseFilter` | 내장 | 되돌아 나오며 응답 본문을 클라이언트로 쓴다 |
| `1` | `RewritePath` | 라우트 | 경로 재작성 (라우트의 `filters:` 선언 순서대로 1부터) |
| `10000` | `RouteToRequestUrlFilter` | 내장 | 라우트의 `uri` + 현재 경로 → 전달 URL 결정 |
| `10150` | `ReactiveLoadBalancerClientFilter` | 내장 | `lb://` 를 실제 인스턴스 주소로 치환 |
| `MAX-1` | `WebsocketRoutingFilter` | 내장 | `ws://`·`wss://` 업그레이드를 가로챈다 |
| `MAX` | `NettyRoutingFilter` | 내장 | 실제 HTTP 호출 |

order 값은 `spring-cloud-gateway-server-webflux` 5.0.0의 바이트코드에서 확인한 것이다.
표에는 주 경로에 놓인 것만 적었다 — 이 게이트웨이가 쓰지 않는 `ForwardRoutingFilter`·
`FunctionRoutingFilter`·`AdaptCachedBodyGlobalFilter` 등은 뺐다.

**자체 필터를 추가할 때 `MIN+30`, `MIN+40`으로 이어 붙인다.** 10 간격은 나중에 사이로
끼워 넣을 자리를 남겨 둔 것이다. `MIN` 근처를 쓰는 이유는 **경로 판정과 로깅이 `RewritePath`
보다 앞이어야 하기 때문**이다(「큰 그림」 참조). 양수 order로 두면 인증이 리라이트된 경로를
보게 되어 화이트리스트가 통째로 어긋난다.

마지막 두 줄이 갈리는 자리가 실시간 스트림이다. **WebSocket은 `WebsocketRoutingFilter`가,
SSE는 평범한 HTTP라 `NettyRoutingFilter`가 처리한다.** 둘 다 `JwtAuthGlobalFilter`를 이미
통과한 뒤이므로 티켓 인증은 어느 쪽이든 같은 자리에서 끝난다.

`JwtAuthGlobalFilter`만 `@Component` 스캔이 아니라 `GatewaySecurityConfiguration`의 `@Bean`이다.
검증기(`ReactiveJwtDecoder`)를 만들지 말지가 `swtp.auth.mode`에 달려 있어서, 필터와 검증기의
생성 조건이 한 화면에 함께 보여야 하기 때문이다.

## 순서도 ① — 정상 요청 전 구간

`GET /master-service/api/master/tags`가 `mode=internal`에서 유효 토큰과 함께 들어온 경우다.
각 단계에서 **요청·응답·exchange 속성이 어떻게 바뀌는지**를 함께 적었다.

```text
① 라우트 매칭 (RoutePredicateHandlerMapping)          — 필터보다 먼저
     속성 + GATEWAY_ROUTE_ATTR = master-service      ← 미매칭이면 여기서 404, 필터는 안 돈다

② RequestIdGlobalFilter                               order MIN
     요청 + X-Request-Id: 3f2b…                       ← 없으면 UUID 발급, 있으면 그대로 이어받음
     응답 + X-Request-Id: 3f2b…                       ← 라우팅 전에 끊겨도 실리도록 먼저 세팅
     속성 + requestId = 3f2b…                         ← 접근 로그가 읽을 자리
     응답에 beforeCommit 훅 등록                       ← ⑨에서 중복을 정리한다

③ AccessLogGlobalFilter                               order MIN+10
     시작 시각만 잡고 그대로 통과                       ← 기록은 doFinally, 즉 ⑨다

④ JwtAuthGlobalFilter                                 order MIN+20
     요청 − X-User-Id · X-User-Roles                   ← 클라이언트가 보낸 값은 무조건 제거
     토큰 검증 (JWKS 서명 · 만료 · typ 클레임)
     요청 + X-User-Id: u-1029                          ← 토큰의 sub
     요청 + X-User-Roles: ADMIN,OPERATOR               ← roles 클레임을 쉼표로 이음

⑤ RewritePath (라우트 필터)                            order 1
     경로   /master-service/api/master/tags
              → /api/master/tags                     ← 서비스명 접두사를 벗긴다

⑥ RouteToRequestUrlFilter                             order 10000
     속성 + GATEWAY_REQUEST_URL_ATTR
              = lb://master-service/api/master/tags    ← 아직 논리 주소다

⑦ ReactiveLoadBalancerClientFilter                    order 10150
     속성 ~ GATEWAY_REQUEST_URL_ATTR
              = http://<internal-host>:36433/api/master/tags  ← Eureka가 준 실제 인스턴스
                                                         없으면 여기서 503

⑧ NettyRoutingFilter                                  order MAX
     실제 HTTP 호출. 응답 헤더를 그대로 복사해 온다

⑨ 되돌아 나오며 (역순)
     응답 ~ X-Request-Id 를 beforeCommit 에서 set()    ← ⑧이 복사해 온 값과 중복되는 것을 1개로
     접근 로그 1건 기록 (doFinally)                     ← ③이 여기서 완성된다
```

**⑤가 ⑥보다 먼저인 것이 `RewritePath`가 성립하는 이유다.** 전달 URL은 라우트의 `uri`와
*그 시점의* 요청 경로를 합쳐 만들어지므로, 경로 재작성이 그보다 뒤에 있으면 아무 효과가 없다.

**⑨의 순서도 의도된 것이다.** 접근 로그를 `doFinally`로 미루는 이유는 SSE·WebSocket 때문이다.
스트리밍 응답은 체인이 즉시 완료되지 않으므로, 종료 시그널(완료·에러·취소) 시점에 기록해야
실제 소요시간과 종료 사유가 정확히 남는다. 그래서 `signal` 필드가 함께 실린다.

## 순서도 ② — 인증 분기

`JwtAuthGlobalFilter` 내부의 결정 트리다. **위에서부터 순서대로 걸린다.**

```text
요청
 │
 ├─ X-User-Id · X-User-Roles 제거                    ← ★ 어떤 분기보다 먼저. 예외 없음
 │
 ├─ swtp.auth.mode = none ?  ──── 예 ──────────────► 통과 (검증하지 않는다)
 │        │ 아니오
 │        ▼
 ├─ HTTP 메서드가 OPTIONS ?  ──── 예 ──────────────► 통과 (CORS 사전 요청)
 │        │ 아니오
 │        ▼
 ├─ permit-all-paths 매칭 ?  ──── 예 ──────────────► 통과 (로그인·JWKS·문서)
 │        │ 아니오                                     판정은 리라이트 이전 외부 경로
 │        ▼
 ├─ Authorization: Bearer 있나 ?
 │        │ 예 ─────────────► 검증 (typ = access 를 요구)
 │        │ 아니오
 │        ▼
 ├─ ticket-auth-paths 매칭 & ?ticket= 있나 ?
 │        │ 예 ─────────────► 검증 (typ = ws-ticket 을 요구)
 │        │ 아니오
 │        ▼
 └────────────────────────────────────────────────► 401 COMMON-401

검증 결과
 ├─ 성공 & typ 일치 ──────────────────────────────► X-User-* 주입 후 통과
 ├─ typ 불일치 ───────────────────────────────────► 401 COMMON-401
 ├─ BadJwtException (서명·만료·형식) ──────────────► 401 COMMON-401
 └─ 그 밖의 JwtException (JWKS 조회 실패) ─────────► 503 COMMON-503  + WARN 로그
```

이 트리에서 순서가 의미를 갖는 자리가 셋이다.

**위조 헤더 제거가 맨 위인 것.** `mode=none`에서도, 화이트리스트 경로에서도 예외 없이 지운다.
*"인증을 안 한다"* 와 *"클라이언트가 자기를 관리자라고 주장할 수 있다"* 는 다른 문제다.
다운스트림이 `X-User-Id`를 로깅·감사에 쓰므로 근거 없는 값이 흘러들면 기록이 오염된다.
화이트리스트 경로에서만 빠뜨려도 그 경로가 통째로 위조 우회로가 된다.

**`OPTIONS`가 화이트리스트보다 위인 것.** 브라우저는 CORS 사전 요청에 `Authorization` 헤더를
붙이지 않는다. 여기서 인증을 요구하면 브라우저를 통한 호출이 전부 깨진다.

**`typ` 클레임 검사.** 액세스 토큰과 WebSocket 티켓이 서로 대체되지 않게 막는다. 유출된 티켓으로
일반 API를 부르는 방향과, 장수명 액세스 토큰을 쿼리 파라미터로 흘리는 방향을 **둘 다** 차단한다.
후자가 중요한 이유는 쿼리스트링이 액세스 로그·Referer·프록시 캐시에 남기 때문이다.

## 필터별 상세

### RequestIdGlobalFilter — `filter/RequestIdGlobalFilter.java`

요청 단위 상관관계 ID를 발급하고 전 구간에 전파한다. 클라이언트가 보낸 `X-Request-Id`는
**그대로 신뢰해 이어받는다** — 호출측이 이미 추적 ID를 갖고 있으면 그 줄기에 붙는 편이 낫고,
게이트웨이가 덮어쓰면 그 연결이 끊긴다.

**왜 `MIN`인가.** 이후 모든 로그가 ID를 가지려면 첫 자리여야 한다. 이 필터보다 앞에서 남는
로그는 상관관계 없이 떠 있게 된다.

**응답 헤더를 두 번 세팅하는 이유.** 처음 `set()`은 라우팅 전에 끝나는 응답(401·503)에도 ID가
실리게 하려는 것이다. 두 번째는 `beforeCommit()` 훅이다 — 다운스트림 서비스도 같은 헤더를 응답에
실어 보내고 게이트웨이가 그 헤더를 그대로 복사하므로, 그냥 두면 응답에 `X-Request-Id`가 **두 번**
실린다. 커밋 직전에 `set()`으로 한 값만 남긴다.

**MDC를 쓰지 않는다.** 리액티브 스택에서는 처리 스레드가 도중에 바뀌므로 스레드로컬인 MDC가
성립하지 않는다. 대신 `exchange`의 속성(`SwtpHeaders.REQUEST_ID_MDC_KEY`)에 넣어 같은 요청을
처리하는 다른 필터가 읽게 한다. 서블릿 스택인 업무 서비스는 `swtp-web-starter`의
`RequestIdMdcFilter`가 헤더를 받아 MDC에 넣는다 — **같은 목적을 스택에 맞는 방식으로 각각 푼다.**

### AccessLogGlobalFilter — `filter/AccessLogGlobalFilter.java`

외부 진입점을 통과한 모든 요청의 라우팅 결과를 남긴다. 로거 이름이 클래스명이 아니라
`"swtp.gateway.access"`라 로그 설정에서 접근 로그만 따로 켜고 끌 수 있다.

필드는 SLF4J fluent API의 key-value로 넣는다. 구조화 로깅(ECS)에서 개별 필드로 직렬화되므로
검색 백엔드에서 정규식 없이 조회할 수 있다.

| 필드 | 출처 | 진단에서의 쓸모 |
|---|---|---|
| `requestId` | exchange 속성 | 서비스 로그와 이어 붙이는 열쇠 |
| `http.method` · `http.path` | 요청 | 리라이트 **이전**의 외부 경로다 |
| `http.status` | 응답 | |
| `gateway.route` | `GATEWAY_ROUTE_ATTR` | 어느 라우트가 잡았는가 |
| `gateway.target` | `GATEWAY_REQUEST_URL_ATTR` | **실제로 어디로 보냈는가** — 라우팅 오설정 진단의 핵심 |
| `duration.ms` | 시작 시각 대비 | |
| `signal` | `doFinally`의 시그널 | 스트리밍에서 정상 종료와 클라이언트 취소를 가른다 |

**왜 `MIN+10`인가.** 요청 ID 발급 **직후**여야 한다. 그래야 로그가 ID를 갖고, 동시에 이후 모든
처리 시간이 측정 구간에 들어온다.

**함정 — `addKeyValue`에 `exchange.getAttribute()`를 인라인으로 넘기지 않는다.** 그 메서드의
시그니처는 `<T> T`라, 인라인으로 넘기면 컴파일러가 `addKeyValue(String, Supplier)` 오버로드를
골라 checkcast를 넣고 런타임에 `ClassCastException`이 난다. 그런데 그 예외가 `doFinally` 안에서
나므로 Reactor가 삼킨다 — **"요청은 200인데 접근 로그만 조용히 사라지는"** 형태로 나타난다.
지역변수로 받아 타입을 `String`으로 확정한 뒤 넘긴다.

### JwtAuthGlobalFilter — `security/JwtAuthGlobalFilter.java`

외부 진입점의 인증 관문이다. 동작은 「순서도 ②」가 전부이므로 여기서는 설계 판단만 적는다.

**Spring Security를 얹지 않는다.** 게이트웨이는 자기 API가 없는 순수 라우터라 인가 규칙이
"경로 화이트리스트 + 토큰 검증"뿐이다. `SecurityWebFilterChain`을 얹으면 인증 판단 지점이
시큐리티 체인과 게이트웨이 필터 **두 군데로 갈라져** 화이트리스트를 양쪽에 중복 관리해야 한다.
서명 검증이라는 어려운 부분은 `ReactiveJwtDecoder`(JWKS 캐싱·kid 선택·만료 검사)에 그대로 위임한다.

같은 이유로 의존도 `spring-boot-starter-security`가 아니라 `spring-security-oauth2-jose`만이다.
전자를 넣으면 Boot의 반응형 시큐리티 자동구성이 켜져 **기본 체인이 모든 요청에 인증을 요구한다.**

**여기서 통과시켜도 서비스가 다시 검증한다(다중 방어).** 게이트웨이를 우회한 직접 호출을 막기
위해서다. 그래서 검증을 끄는 결정(`swtp.auth.mode=none`)도 게이트웨이 단독으로는 성립하지 않는다 —
스위치가 `config-repo`에 있어 게이트웨이와 전 서비스가 같은 값을 받는다.

**왜 `MIN+20`인가.** 접근 로그 **다음**이어야 한다. 401로 끊긴 요청도 접근 로그에 남아야
"누가 언제 무엇을 인증 없이 두드렸는가"를 볼 수 있다. `JwtAuthGlobalFilterTest.runsAfterAccessLog`가
이 관계를 못박는다.

**401과 503을 가르는 이유.** `BadJwtException`(서명 불일치·만료·형식 오류)만 클라이언트 잘못이라
401이고, 그 밖의 `JwtException`은 JWKS 조회 실패(auth-service 다운·네트워크 장애)다. 둘을 401로
뭉뚱그리면 **인증 인프라 장애가 "토큰이 잘못됨"으로 위장된다** — 클라이언트는 재로그인을 반복하고
(그 로그인 API도 함께 죽어 있다) 운영자는 debug 로그를 켜기 전까지 원인을 볼 수 없다.
어느 쪽이든 실패 **사유 자체는** 클라이언트에 알려주지 않는다.

**검증 모드인데 검증기가 없으면 기동을 끊는다.** `Assert.isTrue`가 생성자에 있다. 이 방어가 없으면
모든 요청이 조용히 통과하는데, 그것이 이 필터가 낼 수 있는 최악의 상태다.

## 라우트 필터와 CORS

### RewritePath

`RewritePath=/master-service/(?<segment>.*), /${segment}` 형태로 서비스명 접두사를 벗겨 넘긴다. 라우트의 `filters:` 목록 안 선언 순서대로 order가 1부터
매겨지므로, **GlobalFilter 3종은 언제나 그보다 먼저 돈다.**

**`Path` 술어에 `/**`를 빠뜨리지 않는다.** `Path=/master-service/`는 정확히 그 한 경로만 매칭해
하위 경로가 전부 404가 된다. 라우트는 살아 있고 매칭만 안 되는 상태라 **로그에도 단서가 없다** —
「큰 그림」 ②에서 보았듯 미매칭 요청은 접근 로그를 남기는 필터에 도달조차 하지 못하기 때문이다.

### CORS

`spring.cloud.gateway.server.webflux.globalcors`가 **여기 한 곳에만** 있다. 서비스에서 또
설정하면 헤더가 중복돼 브라우저가 거부한다. `swtp-security-starter`는 그래서 CORS를 끈다.

`allow-credentials: false`인 것이 와일드카드 오리진(`*`)이 성립하는 근거다 — 쿠키가 아니라
Bearer 토큰을 쓰므로 자격증명을 실을 필요가 없고, `credentials=true`였다면 와일드카드가 금지된다.
운영에서는 `SWTP_CORS_ALLOWED_ORIGINS`로 오리진을 고정한다.

`exposed-headers: [X-Request-Id]`가 있어 브라우저 스크립트가 응답에서 요청 ID를 읽을 수 있다.
장애 문의 시 사용자가 ID를 제시할 수 있게 하려는 것이다.

## 헤더 계약

상수는 전부 `libs/swtp-common`에 있다. 게이트웨이(WebFlux)와 서비스(서블릿)는 보안·웹 스타터를
공유할 수 없는데 **같은 값을 같은 뜻으로** 읽어야 하므로, 프레임워크 의존이 최소인 그 라이브러리로
올렸다. 문자열을 각자 하드코딩하면 오타 하나로 "서명은 맞는데 권한이 비는" 조용한 실패가 난다.

| 방향 | 헤더 | 게이트웨이의 처리 |
|---|---|---|
| 클라이언트 → GW | `X-Request-Id` | **신뢰한다.** 있으면 이어받고 없으면 발급 |
| 클라이언트 → GW | `Authorization: Bearer` | 검증에 쓰고 다운스트림에도 그대로 전달 |
| 클라이언트 → GW | `?ticket=` | 티켓 경로에서만 본다 |
| 클라이언트 → GW | `X-User-Id` · `X-User-Roles` | **무조건 제거한다.** 예외 없음 |
| GW → 서비스 | `X-Request-Id` | 발급·전파 |
| GW → 서비스 | `X-User-Id` | 토큰의 `sub` |
| GW → 서비스 | `X-User-Roles` | `roles` 클레임을 쉼표로 이음 (없으면 빈 문자열) |
| GW → 클라이언트 | `X-Request-Id` | `beforeCommit`에서 1개로 정리 |

**서비스는 `X-User-*`를 인증 근거로 쓰지 않는다.** 각자 토큰을 재검증하고, 이 헤더는 로깅·감사·
게이트웨이 경유 여부 판별용 부가 정보다. 그 구분이 무너지면 게이트웨이를 우회한 직접 호출이
헤더 한 줄로 인증을 통과하게 된다.

JWT 클레임은 `SwtpJwtClaims`가 소유한다 — `typ`(`access` / `ws-ticket`) · `roles` · `username`.
역할은 `ROLE_` 접두사 없이 순수 역할명만 담는다.

## 응답 코드를 구분하는 법

같은 숫자가 다른 원인에서 나오므로 접근 로그의 두 필드로 가른다.

| 응답 | 원인 | 접근 로그에서 보이는 것 |
|---|---|---|
| 401 `COMMON-401` | 토큰 없음 · 서명/만료 오류 · `typ` 불일치 | `gateway.route` 있음, `gateway.target` **없음** |
| 503 `COMMON-503` | JWKS를 조회하지 못함 (auth-service 다운) | 위와 같고, `WARN "JWT를 검증할 수 없다"` 가 함께 뜬다 |
| 404 | 어떤 `Path` 술어에도 매칭되지 않음 | **접근 로그가 아예 없다** — 필터 체인을 타지 않았다 |
| 503 (빈 본문) | 라우트는 매칭됐으나 레지스트리에 인스턴스가 없음 | `gateway.target`이 `lb://…` 인 채로 남아 있다 |

마지막 줄이 특히 유용하다. `gateway.target`의 스킴이 `lb://`면 **로드밸런서가 논리 주소를 실제
주소로 바꾸지 못한 것**이고, `http://`면 대상은 찾았는데 그 뒤가 문제라는 뜻이다.

## 함정 기록

1. **화이트리스트·티켓 경로를 리라이트 *후* 경로로 쓰는 것.** 가장 자주 재발한다. 판정은
   `pathWithinApplication()`, 즉 클라이언트가 보낸 그대로의 경로로 이뤄진다. 라우트 접두사를
   바꾸면 `permit-all-paths`와 `ticket-auth-paths`가 함께 바뀌어야 한다. 실제로 이 회귀가
   일어났고 [02](02-경로-규약-확정과-인증-기본값-정렬.md)에서 닫았다.
2. **`X-Request-Id` 중복.** 다운스트림도 같은 헤더를 응답에 싣고 게이트웨이가 그것을 복사하므로,
   `beforeCommit`의 `set()`이 없으면 응답에 두 번 실린다.
3. **`addKeyValue` 오버로드 오선택.** 「AccessLogGlobalFilter」 항목 참조. `doFinally` 안이라
   조용히 삼켜진다.
4. **`Path` 술어의 `/**` 누락.** 하위 경로가 전부 404가 되는데 미매칭 요청은 접근 로그를 남기지
   않으므로 단서가 없다.
5. **서블릿 스택 유입.** 의존을 추가할 때 `spring-boot-starter-web`/`-webmvc` 전이를 exclude한다.
   들어오면 Boot가 웹 타입을 SERVLET으로 판정해 **게이트웨이 자동구성이 통째로, 에러 없이 꺼진다.**

## 알려진 한계

1. ➖ **미검증** — 「큰 그림」 ②의 *"미매칭 요청은 GlobalFilter를 타지 않는다"* 는 프레임워크
   구조(`RoutePredicateHandlerMapping` → `FilteringWebHandler`)에서 유도한 것이고 컨테이너
   실측으로 확인하지 않았다. `AccessLogGlobalFilter.routeId()`의 주석은 *"predicate 미매칭(404)이면
   null"* 이라고 적어 두 서술이 어긋난다. 어느 쪽이든 그 null 분기는 방어 코드로 남겨 둘 값이다.
2. **서비스 간 직접 호출은 상관관계가 끊긴다.** 서비스 간 내부 호출은 게이트웨이를 거치지 않으므로
   (아키텍처 3.1.3) `RequestIdGlobalFilter`만으로는 전 구간을 덮지 못한다. 직접 호출 시 헤더 릴레이가
   별도로 필요하다.
3. **401·503 응답 바디가 `CommonErrorCode`와 두 벌이다.** `JwtAuthGlobalFilter`가 `COMMON-401`·
   `COMMON-503` 문자열을 상수로 복제하고 있어, 코드 체계를 바꾸면 여기가 뒤에 남는다.
   프론트 i18n 키라 갈라지면 조용히 어긋난다.
4. **역할 기반 인가가 게이트웨이에 없다.** 인가 규칙은 "화이트리스트 아니면 유효 토큰" 하나뿐이고,
   `hasRole` 류 판정은 각 서비스가 한다.

## 경로 규약 — 접두사에 묶인 값들

라우트 접두사는 **네 곳에 결합돼 있다.** 하나를 바꾸면 나머지가 함께 바뀌어야 한다.

| 결합된 값 | 위치 | 검증 장치 |
|---|---|---|
| `springdoc.swagger-ui.urls` | 게이트웨이 yml | `ApiDocsRouteConsistencyTest` ✅ |
| `permit-all-paths` | 게이트웨이 yml | `ApiDocsRouteConsistencyTest` ✅ |
| `ticket-auth-paths` | 게이트웨이 yml | **없음** |
| `SWTP_AUTH_JWKS_URI` | compose 2종 · `.env.example` | **없음** |

마지막 둘에 그물이 없다는 것이 실제 사고로 이어졌다. `6bb365d`가 규약을 바꾸고 `f76abf9`가 일부만
되돌리면서 **`ticket-auth-paths`는 SSE·WebSocket 전면 401, compose의 JWKS URL은 `mode=internal`에서
전 요청 503**이 되는 상태가 2주 넘게 살아 있었다. `mode` 기본값이 `none`이라 잠복했고,
`Jenkinsfile`이 `test`를 돌리지 않아 빨간불도 보이지 않았다.

전말과 복원은 [02 경로 규약 확정과 인증 기본값 정렬](02-경로-규약-확정과-인증-기본값-정렬.md)에 있다.

**이 문서가 기술하는 필터 동작은 그 변경의 영향을 받지 않는다** — 바뀐 것은 필터가 읽는 *값*이지
필터가 판정하는 *방식*이 아니다. 다만 「순서도 ②」의 화이트리스트·티켓 경로 판정이
`RewritePath` 이전 경로로 이뤄진다는 사실이 그 사고의 뿌리였으므로, 그 항목은 이 문서에서
가장 중요한 한 줄이다.
