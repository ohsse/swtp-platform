# 관점 판정 — 언제 누구를 소환하고, 언제 중량 리뷰를 도는가

`/step`이 게이트 이전의 전문가 소환과 게이트 이후의 리뷰 깊이를 이 표로 판정한다. 소환·리뷰의 **방법**(배타적 입력, fresh 리뷰어, 3축)은 `/step` 4·7절이 정하고, 이 파일은 swtp-platform에서 **어떤 조건이 어떤 관점을 부르는지**만 정한다.

## 전문가 소환 판정표

| 조건 | 소환 |
|---|---|
| 단일 서비스 안 + 기존 패턴 답습 | **0명** |
| 단일 서비스 안 + **리포에 선례가 없는 패턴·API 계약**(답습할 것이 없음) | **0명** — 단 plan.md에 "선례 확립"임을 명시하고 리뷰는 **중량** |
| 새 테이블·스키마·Flyway 마이그레이션 | 데이터 |
| Kafka 토픽·이벤트 페이로드 변경, 서비스 경계 이동 | 분산 아키텍처 |
| 정수장 운영 규칙·업무 흐름이 얽힘 | 정수장 도메인 |
| compose·리소스·로그/메트릭 계약 변경 | 운영·관측 |
| **불변식 중 하나를 건드림** (`invariants.md`) | **3명 이상 + 반대 의견 plan.md 기록 필수** |

상시 소환하지 않는다. 단순 CRUD에 4명은 낭비고, 그 경험이 반복되면 스킬 자체를 안 쓰게 된다.

## 역할별 입력 — 겹치지 않게 자른다

| 관점 | 읽히는 입력 | 묻는 것 |
|---|---|---|
| 정수장 도메인 | `docs/architecture/` 19장, `docs/erd/`, master 스키마 | 운영 현실에 맞나? 정수장마다 다른가? |
| 데이터 | ERD, Flyway 마이그레이션, hypertable 설계 | 스키마 소유권을 넘나? 데이터 증가율은? |
| 분산 아키텍처 | `docs/architecture/` 3·4장, Kafka 토픽, `docs/scaffold/steps/step-15` | 이벤트 계약이 깨지나? 서비스 경계가 맞나? |
| 운영·관측 | `docs/scaffold/steps/step-16`·`step-17`, compose, ECS 로그 계약 | 단일 서버가 감당하나? 장애 시 보이나? |

## 리뷰 깊이 판정

| 깊이 | 조건 | 구성 |
|---|---|---|
| 경량 | 아래 중량 조건에 하나도 해당하지 않음 | `/code-review` — 코드 변경이 있을 때. 코드 변경 0줄이면 review.md에 "대상 없음"으로 기록 |
| **중량** | 불변식을 건드림 / 여러 모듈에 걸침 / 검증에 `➖ 검증불가` 포함 / 기존 결정을 뒤집음 / 리포 최초 선례 — **하나라도** | `/code-review` + 전용 3축 fresh 리뷰어 |

review.md 첫머리에 어느 깊이였는지와 그 근거(해당한 조건)를 적는다.
