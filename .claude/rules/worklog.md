# 작업일지 — 어디에, 어떤 파일로, 어떤 순서로 남기는가

`/step`이 산출물 경로·양식·파일 전이를 여기서 읽는다. 절차는 스킬(전역)에, 경로와 양식은 이 파일(리포)에 둔다 — 스킬에 경로를 박으면 리포가 바뀔 때 스킬이 썩는다. **이 파일이 작업일지 구조의 단일 출처다.** 스킬이 같은 내용을 다시 적지 않는다.

## 위치 — 무게중심 옆

| 구분 | 위치 |
|---|---|
| 서비스 국소 작업 | `apps/<service>/docs/` |
| 횡단 작업 | 변경의 무게중심 — `libs/docs/` · `starters/docs/` · `infrastructure/docs/` · `build-logic/docs/` · `config-repo/docs/` · 리포 전체면 루트 `docs/` |
| 기각·보류 | **항상 루트** `docs/미착수/<slug>/plan.md` + 루트 `docs/미착수.md`에 한 줄과 링크 — 무게중심이 어디였든 색인과 같은 자리에 모은다 |

여러 모듈에 걸치면 **무게중심에 한 벌만** 두고 나머지에서 링크한다. 변경 내역 표를 그려 보면 무게중심이 드러난다. `docs/scaffold/`는 **동결** — 계속 읽되 새 문서를 추가하지 않는다. 골격 결정을 뒤집을 때만 `docs/scaffold/plan.md` 해당 항목에 취소선 + `→ 철회` 사유를 적는다(기존 기록의 정정이라 동결과 모순되지 않는다).

## 조회 순서 — 코드보다 결정 이력을 먼저

1. 해당 모듈의 `docs/` (단일 파일 `NN-주제.md`와 디렉토리 `NN-<slug>/` 둘 다)
2. `docs/scaffold/steps/` 최신부터 역순 — 특히 「알려진 한계」「미결 사항」「다음 단계」
3. `docs/미착수.md`와 `docs/미착수/` — 접은 주제를 새 사유 없이 재상신하지 않는다
4. `docs/scaffold/plan.md` — 취소선·`→ 철회` 표기 + 「리스크 및 대응」
5. `docs/architecture/` 해당 장
6. 루트 + 모듈 `CLAUDE.md`
7. **그 다음에야 코드**

## 디렉토리 구조 — 작업 하나 = 디렉토리 하나

```
<무게중심>/docs/NN-<slug>/
├── README.md      유일한 진입점. 5필드 요약 + 상태 + 단계 파일 링크
├── plan.md        게이트 산출물. 승인 후 동결 — 이후 한 글자도 고치지 않는다
├── task.md        변경 내역 표 · 구현 상세 · 함정 기록
├── review.md      깊이(경량/중량) · /code-review 결과 · 전용 3축 결과 · 블로커 목록(번호)
├── recycle-N.md   블로커 발생 시. 블로커 인용 · 토의 결론 · task 복귀 방침. N = 1, 2
└── complete.md    실측 결과 · review 블로커 전수 대조 · 알려진 한계 · 다음 단계
```

slug는 기존 파일명 관례대로 한국어 하이픈 연결(`경로-규약-확정과-인증-기본값-정렬`). 2026-10-07 이전의 단일 파일 문서 15개(ems 4·gateway 2·master 5·infrastructure 3·starters 1)는 그대로 둔다 — 완료된 이력은 소급 수정하지 않는다. 번호는 그 디렉토리의 기존 최대값에서 이어간다.

### 번호 — 승인된 순간에만

- 게이트 이전: `docs/<slug>/` **번호 없이** 만든다. 번호 없음 = 미승인의 표식이라 `ls`만으로 미승인 작업이 보인다.
- 승인: 해당 `docs/`의 최대값 + 1을 부여하고 `git mv docs/<slug> docs/NN-<slug>`. README 제목에 `NN`을 끼워 넣는다.
- 기각: `git mv <무게중심>/docs/<slug> docs/미착수/<slug>`(루트) + `docs/미착수.md` 표에 `일자 | 주제 | 사유(한 줄) | 링크`. plan.md 전문이 재상신 때 읽을 근거다.

### README.md 양식

```markdown
# <무게중심> — <제목>            ← 승인 시 "<무게중심> NN — <제목>"으로

- 주제: 한 줄
- 작업일자: YYYY-MM-DD 착수 → YYYY-MM-DD 완료
- 상태: 🔍 계획 | 🔧 진행 | 🧐 리뷰 | ♻ 재작업(N회) | ✅ 완료 | ⛔ 기각 | ⛔ 전환 → <새 slug>
- 토의내용: 결정 요지 한 줄 + 갈린 의견 유무 → [plan.md](plan.md)
- 작업내용: 변경 범위 한 줄 → [task.md](task.md)
- 결과: 완료 조건 충족 여부 한 줄 → [review.md](review.md) · [complete.md](complete.md)
- 관련: 다른 문서 링크
```

### 단계 파일의 절

| 파일 | 절 |
|---|---|
| plan.md | 발단 · 검토 관점(소환한 전문가와 **갈린 의견**) · 결정(**기각한 대안과 사유**) · 영향 범위(모듈·파일) · 기존 결정과의 관계(이어받음/뒤집음/무관) · 불변식 충돌 · **검증 방법**(무엇이 참이면 완료인가 — 착수 전에 정한다) |
| task.md | 변경 내역 표(**변경 없는 영역도 "변경 없음" 행으로** — 빠뜨린 것과 안 건드린 것을 구분) · 구현 상세(경로·계약처럼 나중에 찾을 것) · 함정 기록(빠졌던 함정과 탈출 방법, 리뷰에서 나와 고친 것) |
| review.md | 깊이와 판정 근거 · /code-review 결과 · 전용 3축 결과(명세 대비 구현 / 불변식 / 검증의 진실성) · **블로커 목록 — 번호를 붙인다** |
| recycle-N.md | 인용한 블로커 번호 · 토의 결론 · task.md 어디를 어떻게 고치는가 |
| complete.md | 검증(실행할 명령) · 실측 결과(**실제 출력**, 날짜) · **블로커 대조표** · 알려진 한계(남은 부채, `➖ 검증불가`, 리뷰 지적 중 안 고치기로 한 것과 사유) · 다음 단계(다음 작업의 발단이 된다) |

## 상태 머신 — 파일 전이의 단일 출처

```
🔍 계획 ──승인(번호 부여, git mv)──► 🔧 진행 ──► 🧐 리뷰 ──블로커 없음──► ✅ 완료
   │                                  ▲            │
   └──기각──► ⛔ 기각(미착수/)          └── ♻ 재작업 ◄── 블로커(1·2회째)
                                                   │
                                        3회째 ─────┴──► 토의 강제 → ⛔ 전환(새 slug) 또는 수용 → ✅
```

| 시점 | 파일 | README 상태 |
|---|---|---|
| 게이트 이전 | `<slug>/README.md` + `plan.md` | 🔍 계획 |
| 승인 | `git mv` → `NN-<slug>/`, `task.md` 생성 | 🔧 진행 |
| 기각 | `git mv` → 루트 `docs/미착수/<slug>/`, 색인 한 줄 | ⛔ 기각 |
| 구현 완료 | `review.md` 생성, 깊이 판정부터 | 🧐 리뷰 |
| 블로커 1·2회째 | `recycle-N.md` → task.md 수정 → 검증 재실행 → review.md 갱신 | ♻ 재작업(N회) |
| 블로커 3회째 | recycle 파일을 만들지 않고 토의. 전환이면 README를 `⛔ 전환 → <새 slug>`로 닫고 새 `<slug>/plan.md` | ⛔ 전환 |
| 블로커 없음 / 수용 | `complete.md` | ✅ 완료 |

- README의 `상태`가 현재 위치다. 상태 변경은 README와 해당 단계 파일을 **같은 커밋**에서 한다.
- **recycle은 task로만 돌아간다.** 설계가 유효하고 구현이 틀린 경우다. 전제가 틀렸으면 다른 작업이다 — 원 slug를 전환으로 닫고 새 slug의 plan.md 「발단」에서 원 slug를 가리킨다.
- **3번째 블로커는 구현 문제가 아니라 설계 문제로 본다.** 결론은 전환 또는 (알려진 한계로) 수용 후 완료 둘 중 하나다.

## 세탁 방지 — complete.md의 블로커 대조표

complete.md는 review.md의 블로커를 **번호째 전부** 인용하고 각각 `해소 → task.md 어느 절` 또는 `수용 → 알려진 한계 N` 중 하나를 적는다. 빠진 번호가 하나라도 있으면 `✅`를 쓰지 않는다. plan.md가 동결이므로 "기준을 구현에 맞춰 내리는" 통로는 없다 — 검증 방법이 틀렸다고 판명되면 complete.md에 그 사실과 새 기준을 적고, 원래 기준은 plan.md에 그대로 남는다.

**검증하지 않고 `✅`를 쓰지 않는다.** 컨테이너 기동·외부 환경이 필요해 확인 못 한 항목은 `➖ 검증불가`로 알려진 한계에 남긴다. 확인하겠다고 인프라를 임의로 띄우지 않는다.

## 문체

프론트매터 없음 / H1 아래 불릿 메타 / `---`로 큰 블록만 분리 / 표 적극 사용 / 체크박스 금지 / 한국어 평서형(`~다`) / 기각한 대안과 사유를 남김 / 코드를 읽으면 알 수 있는 것(엔티티 목록·API 경로·클래스 구조)은 쓰지 않음 — 단 「영향 범위」「변경 내역」 표의 파일 나열은 예외다, 거기서는 무엇을 건드렸는지가 곧 내용이다.
