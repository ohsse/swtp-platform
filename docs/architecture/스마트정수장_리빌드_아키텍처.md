# 스마트정수장 서비스 구성안

## 1. 문서 목적

본 문서는 스마트정수장 시스템 구축을 위한 서비스 구성과 기술 아키텍처의 현재 기준안을 정리한다.

현재 시스템은 다음 원칙을 기준으로 설계한다.

- 정수장별 온프레미스 구축
- 대부분의 서비스는 단일 서버에 배포
- 서비스는 기능 단위로 논리적으로 분리
- Java 서비스는 Gradle Multi-Module 기반 Mono Repository로 관리
- 각 서비스는 독립 실행 가능한 Spring Boot Application으로 구성
- 데이터베이스는 PostgreSQL 단일 인스턴스 / 단일 Database 사용
- 시계열 데이터는 동일 PostgreSQL에 TimescaleDB Extension 적용
- Redis 등 별도 공용 메모리 저장소는 현재 사용하지 않음
- 서비스 간 공유 상태가 필요한 경우 PostgreSQL 사용
- 동기 통신은 HTTP 기반
- 비동기 이벤트 전달은 Apache Kafka 사용
- 실시간 Frontend 전달은 WebSocket 또는 SSE 사용
- Batch / Scheduler는 Job Service에서 통합 관리
- 시스템 운영 모니터링은 ELK(Elasticsearch / Kibana / Beats) 기반으로 구성 — 상세는 14장

# 3. 서비스 분류

## 3.1 Infrastructure 영역

### 3.1.1 Config Server

**기술**

- Spring Cloud Config

**역할**

- 서비스 환경설정 중앙 관리
- 정수장별 환경설정 관리
- Database 연결정보 관리
- Kafka 연결정보 관리
- 서비스별 설정값 관리

**운영 기준**

- Discovery Server 의존성을 최소화
- Config Server는 레지스트리에 등록하지 않는다. 다른 서비스가 기동 초기에 설정을 받아야 하는
  대상이므로, 설정을 받기 위해 먼저 레지스트리를 조회해야 하는 순환을 만들지 않는다.
  접근은 `CONFIG_SERVER_URI` 고정 주소로 한다.

---

### 3.1.2 Discovery Server

**기술**

- Netflix Eureka

**배포**

- Core (항상 기동)

**역할**

- 서비스 등록
- 서비스 탐색
- 내부 서비스 위치 확인
- Gateway 및 서비스 간 동적 라우팅 지원

**운영 기준**

- Gateway의 모든 라우트는 `lb://{서비스명}`으로 정의한다. 호스트·포트를 설정에 적지 않으므로
  로컬·컨테이너·다중 노드에서 같은 라우트 목록이 그대로 쓰인다
  (환경별 URI 복제본이었던 `config-repo/gateway-docker.yml`은 이 전환으로 제거되었다).
- 레지스트리에 대상 인스턴스가 없으면 503이다. "라우트 정의가 없다"와 "인스턴스가 없다"가
  응답 코드로 구분된다.
- 단일 노드 배포이므로 자기보호 모드(self-preservation)를 끈다. 켜두면 컨테이너를 내려도
  등록 정보가 남아 Gateway가 죽은 대상으로 라우팅한다.
- 레지스트리 조회 5초 / 하트비트 10초 / 리스 만료 30초. Eureka 기본값(각 30초·30초·90초)은
  "서비스는 떴는데 Gateway는 아직 모르는" 구간을 그만큼 길게 만든다.
- Config Server와 Discovery Server 자신은 레지스트리에 등록하지 않는다.

### 3.1.3 API Gateway

**기술**

- Spring Cloud Gateway
- WebFlux

**역할**

- Frontend의 단일 API 진입점
- API Routing
- 인증/인가 연계
- 공통 Header 처리
- WebSocket Routing
- SSE Routing
- 서비스별 경로 관리

**원칙**

Gateway는 외부 진입점 역할을 담당한다.

서비스 간 내부 호출은 필요한 경우 Gateway를 거치지 않고 직접 HTTP 통신한다.

```text
 │

```

### 3.1.4 API 문서 통합 (Phase 11 확정)

API 문서도 라우팅과 같은 원칙을 따른다 — **단일 진입점**이다.

```text
브라우저
   │  http://<gateway>/swagger-ui.html      ← UI는 게이트웨이 한 곳만 호스팅
   ▼
Gateway (springdoc-openapi-starter-webflux-ui)
   │  드롭다운 선택 시 상대 경로로 스펙 요청
   ├─> GET /master-service/api/master/v3/api-docs        ─> master-service
   ├─> GET /telemetry-service/api/telemetry/v3/api-docs  ─> telemetry-service
   └─> ... 8종
```

**경로 규약**

게이트웨이 라우트는 `Path=/{서비스명}/**`이고 `RewritePath`가 그 접두사를 벗겨 서비스에 넘긴다
(step-18에서 전 라우트 통일). 따라서 **게이트웨이에서 본 주소와 서비스가 노출하는 경로가 갈린다** —
브라우저는 `/{서비스명}/api/{prefix}/...`를, 서비스는 `/api/{prefix}/...`를 본다.

서비스는 문서를 `/api/{prefix}/v3/api-docs`에 노출한다 — springdoc 기본값 `/v3/api-docs`에 두면
게이트웨이를 통해 도달할 라우트가 존재하지 않는다. 이 경로는 `swtp-web-starter`가
`spring.application.name`에서 `-service`를 떼어 자동 주입하므로 서비스가 따로 설정하지 않는다
(`master-service` → `/api/master/v3/api-docs`, 게이트웨이 경유 주소는 `/master-service/api/master/v3/api-docs`).

**스펙 규약 — 두 가지를 web-starter가 강제한다**

| 항목 | 값 | 이유 |
|---|---|---|
| `servers` | `/` (상대) | springdoc 기본값은 요청 Host로 계산한다. 게이트웨이가 프록시하면 서비스가 보는 Host는 컨테이너 내부 이름이라 브라우저가 도달할 수 없는 주소가 스펙에 박힌다. 상대 URL은 게이트웨이 경유와 서비스 직접 접근 양쪽에서 옳다 |
| `securitySchemes.bearerAuth` | HTTP bearer / JWT | 집계 UI의 Authorize 버튼은 *선택된 스펙*이 선언한 스킴만 노출한다. 서비스가 각자 선언하면 한 곳만 빠뜨려도 그 서비스만 토큰 입력이 불가능해진다 |

**문서 경로는 인증 화이트리스트로 열려 있다.** UI가 뜨기 전에는 토큰을 얻을 화면 자체가 없으므로
불가피하다. 운영에서 스펙 노출을 막아야 한다면 운영 프로파일에서 `springdoc.api-docs.enabled=false`로
끄거나, 게이트웨이 화이트리스트에서 문서 경로를 제외하고 내부망 접근으로 제한한다.

# 4. 업무 서비스

## 4.1 Auth Service

**배포**

- Optional

정수장에 기존 인증/인가 시스템이 존재하거나 인증 자체가 필요 없는 경우 배포하지 않을 수 있다.

**역할**

- 로그인
- JWT 발급
- 사용자 관리
- Role 관리
- Permission 관리
- 인증/인가 정책 관리

**검증 모드 규약** (`swtp.auth.mode`)

정수장마다 인증 체계가 다른 현실을 설정 한 줄로 흡수한다. 실제 배포 현실은 **토큰을 검증하는
정수장과 하지 않는 정수장 둘**이므로 두 값만 둔다.

| 모드 | 동작 | 함께 지정할 값 |
|---|---|---|
| `none` (기본) | 검증하지 않고 통과시킨다. 인증·인가를 앞단 포털/SSO가 끝내는 정수장과 인증 체계가 없는 폐쇄망 | — |
| `internal` | auth-service가 발급한 토큰을 검증한다 | `swtp.auth.jwks-uri` |

- **스위치는 `config-repo`에 한 곳만 둔다.** Gateway와 각 서비스가 독립적으로 검증하는
  다중 방어 구조이므로, Gateway에서만 꺼도 서비스가 401을 낸다. 서비스별로 설정하게 두면
  한쪽만 바뀐 상태가 성립하고 그 증상은 "설정은 맞는데 호출이 안 되는" 형태로 나타난다.
- **결정 주체는 `SWTP_AUTH_MODE` 환경변수다.** `mode`와 `jwks-uri`(`SWTP_AUTH_JWKS_URI`)는
  **한 쌍으로만** 의미가 있으므로 함께 지정한다. 둘을 따로 두면 "검증은 켜져 있는데 공개키는
  없는 곳을 가리키는" 상태가 성립한다. Spring 프로파일은 환경 축(`docker`) 하나다.
- **외부 IdP를 값으로 두지 않는 이유**: 검증 경로가 자체 발급 토큰 규약에 결합돼 있다.
  Gateway가 요구하는 `typ` 클레임(액세스 토큰과 WebSocket 티켓을 구분하려고 우리가 넣는
  커스텀 클레임)이 표준 IdP 토큰에는 없어, 값만 늘려서는 서명이 맞아도 전 요청이 401이 된다.
  쓰지 않는 선택지를 남겨 "설정은 있는데 전부 401"인 상태를 만들지 않는다.
  외부 IdP 연동이 실제로 필요해지면 그때 클레임 규약부터 함께 설계한다.
- **`internal`인데 `jwks-uri`가 비어 있으면 기동을 끊는다.** 여기서 끊지 않으면 첫 요청이
  들어올 때까지 정상으로 보이다가 모든 호출이 401이 된다.
- **JWKS를 조회하지 못하면 401이 아니라 503이다.** 서명 불일치·만료(`BadJwtException`)만
  401이고, auth-service 다운·네트워크 장애로 검증 자체가 불가능한 경우는 503으로 구분한다.
  둘을 뭉뚱그리면 인증 인프라 장애가 "토큰이 잘못됨"으로 위장돼, 클라이언트는 함께 죽어 있는
  로그인 경로로 재시도만 반복한다.
- **`none`의 부작용**: 감사 컬럼(`rgstr_id`/`mdf_id`)은 전부 시스템 기본값(`SYSTEM`)으로 기록된다
  — 사용자를 식별할 근거가 애초에 없다. 또한 인증 주체가 없으므로 `@PreAuthorize` 같은 메서드
  단위 권한은 통과하지 못한다(403). **권한 규칙이 붙은 API가 생기는 순간 이 모드는 성립하지 않는다.**
  기동 시 경고 로그를 남기되 기동을 막지는 않는다 — 인증 체계가 없는 폐쇄망은 실제 배포 형태다.
- `none` 모드에서도 Gateway는 클라이언트가 보낸 `X-User-Id`/`X-User-Roles`를 제거한다.
  "인증을 하지 않는다"와 "클라이언트가 자기를 관리자라고 주장할 수 있다"는 다른 문제다.

**토큰 규약** (Phase 10 확정)

- **RS256 비대칭 서명**. auth-service만 개인키를 보유하고, 공개키는 `GET /api/auth/.well-known/jwks.json`(RFC 7517)으로 배포한다.
  대칭키는 전 서비스가 서명키를 공유해야 해 채택하지 않는다 — 서비스 한 곳이 뚫리면 토큰 위조가 가능해진다.
- **발급은 auth-service 단독, 검증은 Gateway와 각 서비스가 각자 수행한다.** 검증 측은 서명키를 모르고
  `swtp.auth.jwks-uri` 하나만 안다 — 다른 서비스가 auth-service를 직접 호출하지 않으므로,
  배포하지 않는 정수장에서 이 앱만 통째로 빠질 수 있다(Optional 요건).
- **Gateway 통과가 곧 신뢰는 아니다(다중 방어).** Gateway가 주입하는 `X-User-Id`/`X-User-Roles`는
  로깅·감사용 부가 정보이며, 각 서비스는 토큰을 다시 검증한다. Gateway를 우회한 직접 호출도 401이 된다.
  클라이언트가 보낸 동명 헤더는 Gateway가 인증 여부와 무관하게 항상 제거한다.

| 토큰 | `typ` | 유효기간 | 검증 방식 | 폐기 |
|---|---|---|---|---|
| 액세스 토큰 | `access` | 30분 | 서명 (상태 조회 없음) | 불가 — 짧은 만료로 대응 |
| 리프레시 토큰 | (JWT 아님, 불투명 난수) | 14일 | DB 조회 (SHA-256 해시 대조) | 가능. 매 사용 시 회전하며, 폐기된 토큰 재제출은 탈취로 보고 해당 사용자 전체 토큰을 끊는다 |
| WebSocket 티켓 | `ws-ticket` | 30초 | 서명 | 불가 — 초단기로 대응 |

토큰 용도(`typ`)는 양방향으로 잠근다. 티켓으로 일반 API를 호출할 수 없고, 액세스 토큰을 쿼리 파라미터로 넘길 수도 없다.

**Redis를 쓰지 않으므로**(원칙 15) 사용자·역할·리프레시 토큰·서명 키쌍은 모두 PostgreSQL `auth` 스키마에 둔다(원칙 16).

## 4.3 EMS Service

**배포**

- Core (항상 기동)

에너지 관리는 전 정수장 공통 요구사항으로 확정되어 Core로 승격했다(19장 예시 A·B 모두 EMS를
포함한다). compose profile 없이 기본 기동 대상이며, 정수장별 선택 배포에서 제외된다.

**역할**

## 7.3 인증 방식 (Phase 10 확정)

브라우저의 `EventSource`(SSE)와 `WebSocket` API는 **핸드셰이크에 임의 헤더를 붙일 수 없다.**
따라서 다른 API처럼 `Authorization: Bearer`로 자격을 넘길 수 없고, 쿼리 파라미터를 쓸 수밖에 없다.

액세스 토큰을 그대로 쿼리 파라미터에 넣는 방식은 채택하지 않는다 — URL은 액세스 로그, `Referer` 헤더,
프록시 캐시, 브라우저 히스토리에 남으므로 30분짜리 토큰이 여러 곳에 복제된다.

**단기 티켓 방식**을 쓴다.

```text
1) 클라이언트가 액세스 토큰으로 POST /api/auth/ws-ticket 호출
2) auth-service가 typ=ws-ticket, 유효기간 30초짜리 JWT를 발급
3) 클라이언트가 wss://.../realtime-service/api/realtime/...?ticket=<티켓> 으로 접속
4) Gateway가 티켓을 검증(서명 + typ) 후 X-User-Id / X-User-Roles를 주입해 전달
```

- 티켓은 별도 저장소 없이 **서명만으로 검증**한다. 유효기간이 30초라 폐기 목록이 필요하지 않다.
- `typ`으로 용도를 잠그므로 티켓을 일반 API 호출에 재사용할 수 없다.
- Gateway는 `swtp.gateway.security.ticket-auth-paths`에 등록된 경로(현재 `/realtime-service/**`)에서만
  쿼리 파라미터 인증을 허용한다.

# 11. Database 구성

## 11.1 기본 원칙

현재 시스템에서는 서비스별 Database를 분리하지 않는다.

```text
PostgreSQL Instance : 1
Database            : 1
TimescaleDB          : Extension
Redis                : 미사용
```

모든 서비스는 동일 PostgreSQL을 사용한다.

### 공통 감사 컬럼 규약

모든 업무 테이블은 아래 컬럼명을 따른다. 값은 애플리케이션(JPA Auditing)이 채우므로 **DB DEFAULT를 걸지 않는다** —
DB와 애플리케이션이 함께 채우면 "누가 채웠는지"가 두 곳으로 갈려 추적이 어려워진다.

| 컬럼 | 타입 | NULL | 의미 |
|---|---|---|---|
| `rgstr_dttm` | `TIMESTAMP` | NOT NULL | 등록일시 (불변) |
| `rgstr_id` | `VARCHAR(50)` | NOT NULL | 등록ID — 토큰의 `sub`. 인증 컨텍스트가 없으면 `SYSTEM` |
| `mdf_dttm` | `TIMESTAMP` | NOT NULL | 수정일시 — 등록 시점에 `rgstr_dttm`과 같은 값으로 채워진다 |
| `mdf_id` | `VARCHAR(50)` | NOT NULL | 수정ID — 등록 시점에 `rgstr_id`와 같은 값으로 채워진다 |

**핵심 원칙: 컬럼이 있으면 값이 반드시 있다.** "컬럼은 있는데 값이 NULL"인 상태는 존재하지 않는다.

**모든 테이블이 수정 컬럼을 갖지는 않는다.** 등록만 하고 수정하지 않는 테이블(이력·로그·매핑 테이블 등)은
`mdf_dttm`/`mdf_id`를 **아예 두지 않는다**. 수정 컬럼이 NOT NULL인 이상 이런 테이블에 형식적으로 붙이면
등록값을 복사하는 것 말고는 채울 값이 없고, 전 행이 `mdf_dttm = rgstr_dttm`인 무의미한 컬럼 두 개가 남는다.
**수정 컬럼의 존재 여부가 곧 "이 테이블이 수정되는가"의 선언이다.**

```text
등록만       →  BaseCreatedEntity 상속   (rgstr_dttm, rgstr_id)
등록 + 수정  →  BaseEntity 상속           (+ mdf_dttm, mdf_id — 모두 NOT NULL)
```

- 수정 컬럼은 **등록 시점에 등록값과 동일하게 함께 채워진다**(`modifyOnCreate` 기본값 `true`).
  따라서 "한 번도 수정되지 않음"은 `mdf_dttm = rgstr_dttm`으로 판정한다. 최종 변경 시각은 `mdf_dttm` 하나로 얻는다.
- **벌크 UPDATE를 쓰지 않는다.** JPQL `update` 문이나 네이티브 SQL은 `AuditingEntityListener`를 우회해
  수정 컬럼을 그대로 두므로 이력이 옛 값에 멈춘다. 변경은 반드시 엔티티를 로드해 필드를 바꾸는 방식으로 표현한다.
- 감사 컬럼은 시간대 없는 `TIMESTAMP`를 쓴다. 시계열 **측정·이벤트 시각**은 `TIMESTAMPTZ`를 유지한다 —
  전자는 "누가 언제 입력했는가"라는 운영 기록이고, 후자는 데이터 자체의 값이라 성격이 다르다.
- 감사 컬럼이 있는 매핑 테이블은 JPA `@ManyToMany`로 매핑하지 않는다. 조인 테이블은 Hibernate가 직접
  INSERT/DELETE하므로 감사 컬럼이 채워지지 않아 NOT NULL 위반이 난다 — 반드시 엔티티로 드러낸다.
- 애플리케이션을 거치지 않는 **시드/마이그레이션 INSERT는 감사 컬럼 네 개를 모두 직접 채운다**.
  등록 주체는 `SYSTEM`을 쓴다 — 스타터의 `AuditorProvider` 기본값과 같아 이력이 일관되게 읽힌다.

## 11.3 Database 공유와 데이터 소유권

물리 Database는 공유하지만 서비스별 데이터 책임은 유지한다.

예:

```text
Master Service
    │
    └─ master.* 생성/수정 책임


Telemetry Service
    │
    └─ telemetry.* 생성/수정 책임


EMS Service
    │
    └─ ems.* 업무 데이터 책임
```

다른 서비스가 임의로 다른 영역의 데이터를 수정하지 않도록 한다.

**명시적 예외 — `operation` 스키마 (제어 이력 공용 write)**

자율운영(autonomous-service)과 EMS(ems-service)는 제어 대상 설비가 겹칠 수 있다
(예: 밸브 개도 — autonomous는 송수를 제외한 공정을, ems는 송수펌프·밸브를 제어).
제어 이력을 서비스별로 나누면 "이 설비를 방금 누가 건드렸나"를 판단할 수 없고
사고 조사용 감사(audit) 로그가 스키마 경계로 쪼개진다. 따라서 `operation`은
소유권 원칙의 명시적 예외로 둔다 (job-service가 `batch`/`quartz`까지 겸유 소유하는
선례와 동일 계열):

```text
operation.control_command   -- 제어 명령 통합 이력 (공용 write)
  issuer_service             -- 'autonomous' | 'ems' | 'manual'
  target_facility_id         -- master.facility 참조
  command_type / value / reason / result / executed_at

operation.operation_mode    -- 공정별 운전모드 (자동/수동/원격)
```

- DDL(Flyway) 소유는 **master-service** — core 상시 기동이며 제어 대상 기준정보(설비/태그)를
  이미 소유하고 있어 FK 정합이 자연스럽다.
- write는 제어 권한을 가진 서비스가 공동으로 수행한다. 명령과 같은 트랜잭션에 동기 기록하고,
  필요 시 `operation.control` 토픽으로 비동기 발행해 realtime/알람이 소비한다 (Kafka로 이력
  자체를 비동기 적재하지 않는다 — 감사 데이터의 정합성이 우선).

# 12. TimescaleDB

## 12.1 구성

TimescaleDB는 별도 Database가 아니라 PostgreSQL Extension으로 사용한다.

```text
PostgreSQL
    +
TimescaleDB Extension
```

## 12.2 적용 대상

```text
telemetry.tag_value
telemetry.prediction_value
telemetry.aggregate_value
```

등 시계열 데이터 테이블에 적용한다.

**경계 규칙 — 원천은 telemetry, 업무 파생 지표는 각 서비스**

telemetry는 "센서가 만든 값"과 그 직접 파생(예측·집계)만 소유한다. 업무 로직이 만든
지표(예: ems의 전력 원단위 kWh/㎥ 추이, pms의 설비 이상진단 점수 추이)는 해당 업무 서비스가
자기 스키마에 hypertable로 소유한다 (`ems.energy_intensity`, `pms.health_score` 등).
TimescaleDB extension은 DB 단위 1회 설치로 전 스키마에서 공유되므로 기술 제약은 없다.

근거는 19장 "정수장별 선택 배포"다. ems/pms는 compose profile로 선택 배포되는 optional
서비스다. 파생 지표를 telemetry에 두면 ems를 배포하지 않는 정수장에도 ems 전용 hypertable이
telemetry 스키마 안에 잔류해 스키마 단위로 걷어낼 수 없다. 각자 스키마에 두면 서비스를
배포하지 않는 정수장은 스키마 자체를 생략할 수 있다.

## 12.3 초기 운영 기준

현재 예상 기준:

- 정수장별 태그 수: 최대 약 1,000개 미만
- 수집 주기: 분 단위 중심
- Hypertable 사용
- 초기 Chunk Interval: 7일
- HASH Partition: 초기 미적용

데이터 증가량 및 Query Pattern 확인 후 조정한다.

# 14. Observability

관측 백엔드는 **ELK**다. 고객사 요구사항 SFR-016이 ELK 기반 상태 정보 제공을 강제한다.
초기 설계(Prometheus / Loki / Alloy / Grafana)는 step-16에서 철거했고, 이 장은 그 후속인 step-17의 결과를 기술한다.

**앱 계측 층은 교체 대상이 아니었다.** Micrometer/Actuator, ECS JSON 로그, `X-Request-Id` 상관관계는 전부 벤더 중립이라 그대로 남았고, 실제로 ELK 도입 시 Java 앱 11종의 코드 변경은 0줄이었다. 바뀐 것은 백엔드와 수집기뿐이다.

```text
      Application (Java 11종 + FastAPI)
            │                    │
     /actuator/prometheus      stdout (ECS JSON 1줄)
      (OpenMetrics)                │
            │                      │
            ▼                      ▼
       Metricbeat              Filebeat
     (+ docker 모듈)      (docker autodiscover)
            │                      │
            └──────────┬───────────┘
                       ▼
                 Elasticsearch
                       │
                       ▼
                    Kibana
```

배포는 compose의 `elk` 프로파일이다. **앱 프로파일(`full`)과 다른 축이라 함께 묶지 않는다** — `full`은 Optional *앱* 묶음이고 ELK는 앱이 아니다.

## 14.1 Elasticsearch

로그와 메트릭의 단일 저장소. 별도의 메트릭 DB를 두지 않는다 — 두 종류를 한 곳에 두어야 Kibana에서 같은 필터(`service.node.name`, `service.name`)로 함께 좁힐 수 있다.

- 단일 노드(`discovery.type: single-node`). 정수장당 서버 1대이므로 복제본을 배치할 곳이 없다 — 클러스터 상태 `yellow`가 정상이다.
- **보안 비활성**(`xpack.security.enabled: false`) — 폐쇄망 전제. 대신 9200을 루프백에만 공개해 노출면을 없앤다. 중앙 집계로 전환하면 반드시 다시 켠다.
- 힙은 명시 고정한다(기본 1GB). 자동 산정은 가용 메모리의 절반을 잡는데, 단일 서버에 앱 11종 + Kafka + TimescaleDB가 이미 올라가 있어 과하다.
- 보존 정책(ILM)은 `elk-init` 컨테이너가 박는다 — 기본 30일 / 주 샤드 5GB.

## 14.2 Filebeat

로그 수집 Agent. **컨테이너 stdout이 유일한 수집 진입점**이며, 파일 로그(`logs/<service>/`)는 사람이 직접 여는 감사·장애분석용 백업이라 수집기가 읽지 않는다(이중 적재 방지).

- docker autodiscover로 컨테이너를 발견하고 `^swtp-` 정규식으로 거른다 — 호스트의 무관한 컨테이너 로그 유입 차단
- `container` 파서로 Docker 껍데기를 벗기고 `ndjson` 파서로 ECS JSON을 필드로 펼친다
- 평문 로그(Kafka, TimescaleDB 등)는 파싱 실패를 무시하고 `message` 그대로 통과시킨다 — 이들도 장애 분석에 필요하다
- 수집 위치(registry)는 볼륨에 영속화해 재시작 시 중복/누락을 막는다

**수집 대상 (컨테이너 stdout)**

```text
Gateway / Auth / Autonomous / EMS / PMS / Master / Telemetry / Job / Realtime
Config Server / Discovery Server / FastAPI(ai-service)
Kafka / TimescaleDB / ELK 자신
```

## 14.3 Metricbeat

메트릭 수집 Agent. 두 모듈을 쓴다.

| 모듈 | 대상 | SFR-016 대응 |
|---|---|---|
| `docker` | 컨테이너 상태(up/exited/restarting) · healthcheck 결과 · CPU · Memory · Network · DiskIO | "도커 내부 프로세스가 정상 동작하는지 모니터링" |
| `prometheus` | 각 앱의 `/actuator/prometheus` (OpenMetrics 표준) | "운영 정보를 취합하여 정상/장애 모니터링" |

**주요 메트릭** — Micrometer/Actuator 자동 수집분이며 커스텀 계측은 두지 않는다.

- JVM Heap / GC / Thread
- CPU / Memory
- HTTP Request / Error / Response Time
- DB Connection Pool
- Kafka Producer/Consumer
- 컨테이너 상태 및 healthcheck

`docker` 모듈의 healthcheck 메트릭셋은 compose의 `depends_on` 체인이 쓰는 그 healthcheck 결과를 읽는다 — **별도 계측 없이 기존 자산이 그대로 모니터링 신호가 된다.**

`ai-service`는 actuator가 없어 `prometheus` 모듈 대상이 아니다. 컨테이너 상태는 `docker` 모듈이, 알고리즘 모델 프로세스 상태(생존 / 마지막 추론 시각 / 추론 에러율)는 자기 ECS 로그가 보고한다.

## 14.4 Kibana

통합 운영 Dashboard. **SFR-016의 "ELK 기반 상태 정보 제공"은 Kibana 대시보드로 충족한다** — 플랫폼 자체 화면 임베드나 자체 API 재노출은 별도 요구로 분리한다.

- 로그 조회 (Discover, 데이터 뷰 `filebeat-*`)
- 컨테이너·서비스 상태 대시보드 (`[Metricbeat Docker] Overview ECS`)
- 메트릭 시각화 (데이터 뷰 `metricbeat-*`)
- 장애 분석 — `requestId` 하나로 게이트웨이부터 AI 서비스까지 한 요청의 전 구간을 묶어 본다
- Alert

## 14.5 상관관계와 정수장 식별

| 축 | 필드 | 발급/설정 |
|---|---|---|
| 요청 | `requestId` | 게이트웨이가 발급(`X-Request-Id`), 전 구간 전파. Java는 MDC, Python은 ContextVar |
| 서비스 | `service.name` | `spring.application.name` (Python은 상수) |
| 정수장 | `service.node.name` | `SWTP_SITE_CODE` 환경변수 → ECS 표준 노드 슬롯 |

**정수장 식별자를 커스텀 필드가 아니라 ECS 표준 슬롯에 싣는다.** 표준 슬롯이면 Beats 템플릿과 Kibana 기본 매핑이 그대로 먹고, 수집기를 갈아타도 같은 자리에 남는다. 이 필드가 중앙 집계 전환의 전제조건이다 — 나중에 채우면 이미 적재된 인덱스를 재색인해야 한다.

**분산 트레이싱은 도입하지 않는다.** 상관관계는 `requestId`까지만 성립한다(step-09 결정). 단일 서버·정적 라우팅 규모에서 트레이싱 백엔드의 운영 비용이 얻는 것보다 크다.

# 15. 공통 Starter / Library

## 15.1 swtp-security-starter

- JWT 검증
- 인증/인가
- SecurityContext Utility
- Claim 처리
- 권한 공통 처리

**서블릿 전용이다.** Gateway는 WebFlux라 이 스타터를 쓰지 않고 자체 `GlobalFilter`로 검증한다
(`@ConditionalOnWebApplication(SERVLET)`으로 강제). 그래서 발급·검증 양쪽이 공유해야 하는
클레임 이름과 헤더 이름은 `swtp-common`에 둔다.

**토큰을 발급하지 않는다.** 서명키를 보유하지 않고 `swtp.auth.jwks-uri`로 받은 공개키로만 검증한다.

| 구성 요소 | 역할 |
|---|---|
| `SwtpPrincipal` / `@CurrentUser` | 컨트롤러가 `Jwt` 원본을 보지 않게 하는 방화벽 — 토큰 포맷 변경의 영향 범위를 스타터 안에 가둔다 |
| `SwtpSecurityContext` | 컨트롤러 파라미터를 받을 수 없는 서비스 계층용 조회 유틸 |
| `SwtpSecurityProperties` | `permit-all-paths`(플랫폼 기본) + `public-paths`(앱 추가분)의 **합집합**. 리스트 프로퍼티는 병합이 아니라 치환이라 하나로 두면 앱이 재정의하는 순간 actuator가 닫힌다 |
| `SecurityContextAuditorProvider` | 감사 컬럼(`rgstr_id`/`mdf_id`)에 로그인 사용자 공급 |
| `SwtpSecurityErrorResponder` | 401/403을 공통 응답 봉투로 — 필터 단계 오류는 `@RestControllerAdvice`를 타지 않는다 |
| `testFixtures` | 각 서비스 통합 테스트가 auth-service 없이 토큰을 발급·검증하기 위한 픽스처 |

## 15.5 swtp-common

| 구성 요소 | 내용 |
|---|---|

| `ApiResponse` / `ErrorCode` / `BusinessException` | 공통 응답 봉투와 에러 코드 계약 |

# 19. 정수장별 선택 배포

정수장별 요구사항에 따라 업무 서비스를 선택적으로 배포할 수 있다.

## 예시 A — 인증 안 함

```text
Gateway
Master
Telemetry
Job
EMS
PMS
```

## 예시 B — 인증 함

```text
Gateway
Auth
Master
Telemetry
Job
Autonomous
EMS
PMS
AI
Realtime
```

Core 및 Infrastructure 구조는 최대한 동일하게 유지하고 Optional Service만 변경한다.

**선택 대상**

- Optional Service: `auth` / `autonomous` / `pms` / `ai` (compose profile, 묶음 `full`)
- EMS는 위 예시 A·B 모두에 포함되어 사실상 전 정수장 공통이므로 Core로 승격했다(4.3 참조).
- Discovery Server도 Core다 — Gateway의 `lb://` 라우팅이 이것 없이는 성립하지 않는다(3.1.2 참조).

**컨테이너 선택과 설정 선택은 별개 축이다**

| 축 | 수단 | 예 |
|---|---|---|
| 어떤 컨테이너를 띄울지 | compose `--profile` | `--profile auth` |
| 어떤 설정을 읽을지 | `SWTP_PROFILES` (Spring) | `docker` |

```bash
# auth-service 배포
docker compose -f infrastructure/docker/compose.yaml --profile auth up -d --build
# auth-service 미배포
docker compose -f infrastructure/docker/compose.yaml up -d --build
```

Spring 프로파일은 환경 축(`docker`) 하나이므로 `compose.yaml`은 전 정수장 동일하고,
정수장별 차이는 어떤 컨테이너를 띄우는가뿐이다. 인증 모드(`swtp.auth.mode`)는
`SWTP_AUTH_MODE` 환경변수가 결정하지만 현재 compose가 이를 컨테이너에 전달하지 않으므로,
정수장별로 켜고 끄려면 `x-app-env`에 전달을 먼저 추가해야 한다. 모드의 제약은 4.1을 참조한다.

# 20. 핵심 설계 원칙

1. 서비스는 기능별로 논리적으로 분리한다.
2. 현재는 대부분의 서비스를 단일 서버에 배포한다.
3. Java 서비스는 Gradle Multi-Module Mono Repository로 관리한다.
4. 각 Application Module은 독립 실행 가능한 Spring Boot Application으로 유지한다.
5. Application Module 간 직접 Gradle Dependency를 만들지 않는다.
6. 서비스 간 동기 호출은 HTTP를 사용한다.
7. 비동기 이벤트와 데이터 스트림은 Kafka를 사용한다.
8. Database는 PostgreSQL 단일 Instance / 단일 Database를 사용한다.
9. 서비스별 Database는 분리하지 않는다.
10. 기능별 Schema를 통해 논리적 데이터 영역을 구분할 수 있다.
11. 물리 DB는 공유하더라도 데이터 소유권은 서비스별로 관리한다.
12. 시계열 데이터는 TimescaleDB Hypertable을 사용한다.
13. 초기 TimescaleDB Chunk Interval은 7일을 기준으로 검토한다.
14. 초기에는 HASH Partition을 사용하지 않는다.
15. Redis는 현재 사용하지 않는다.
16. 공유 영속 상태가 필요하면 PostgreSQL을 사용한다.
17. Quartz는 실행 시점 및 스케줄 관리 역할을 담당한다.
18. Spring Batch는 Dataset 생성, 집계, 대량 처리 및 재처리를 담당한다.
19. Job Service는 Web API를 제공하여 수동 실행을 지원한다.
20. 자동 실행과 수동 실행은 동일한 업무 로직을 사용한다.
21. Frontend는 Kafka에 직접 연결하지 않는다.
22. 실시간 데이터는 Realtime Service를 통해 WebSocket/SSE로 제공한다.
23. Metricbeat는 컨테이너 상태와 Application Metrics를 담당한다.
24. Filebeat는 컨테이너 stdout의 ECS JSON Log를 담당한다.
25. Kibana는 시스템 운영 상태를 통합 시각화한다.
26. 정수장별 요구사항에 따라 Optional Service를 선택 배포한다.
