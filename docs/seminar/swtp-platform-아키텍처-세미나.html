기능은 나누되, 서버는 하나

독립 실행 앱으로 논리 분리하되 배포는 한 서버 위 compose입니다. 노드를 늘릴 때 코드가 아니라 배포 방식만 바뀝니다.

모노레포 · Gradle 멀티모듈

리포를 쪼개면 공통 코드 버전이 정수장 수만큼 갈라집니다. 한 리포에서 한 번에 빌드합니다.

단일 DB · 스키마로 분리

PostgreSQL 인스턴스 하나. 서비스별 DB를 나누지 않고 스키마로 논리 분리합니다.

Redis를 쓰지 않는다

단일 서버에서 미들웨어 하나는 곧 메모리 하나이자 운영 대상 하나입니다. 공유 상태는 PostgreSQL에 둡니다.

# 층마다 역할이 하나다
build-logic 규칙 · libs 계약
starters 기본 동작 · apps 업무

# 모듈 트리의 단일 진실
settings.gradle

앱 모듈 간 project() 의존을 금지합니ㅅ다

EMS가 Master의 엔티티를 Gradle 의존으로 끌어오는 순간, 두 서비스는 같이 빌드되고 같이 배포되어야 하는 한 덩어리가 됩니다. 논리적으로 나눈 의미가 사라집니다. 공유가 필요하면 libs/starters로 올리거나, HTTP·Kafka로 통신합니다.

이 규칙은 리뷰가 아니라 빌드가 지킵니다

swtp.spring-boot-app 규약이 클래스패스를 훑어 :apps:로 시작하는 project 의존이 있으면 configuration 시점에 예외를 던집니다.

앱 모듈 간 직접 의존은 금지된다:
  :apps:ems-service -> [:apps:master-service]
Invariants & Conventions

일곱 개의 불변식, 네 개의 규약 플러그인

  1. 앱 모듈 간 project() 의존 금지. 빌드가 실패시킵니다.
  2. 버전은 gradle/libs.versions.toml에서만. build.gradle에 버전 문자열을 쓰지 않습니다 — BOM이 정렬합니다.
  3. DDL은 Flyway 단독 소유(ddl-auto: none). 스키마 생성만 init SQL이 합니다.
  4. Redis 미사용. 공유 영속 상태는 PostgreSQL에 둡니다.
  5. 통합 테스트에 H2 금지. 운영과 같은 이미지의 Testcontainers를 씁니다.
  6. Spring Boot 4 이름 체계를 씁니다.
  7. 주석·문서·커밋 메시지는 한국어로 씁니다.
플러그인담고 있는 것
swtp.java-commontoolchain 21, UTF-8, JUnit Platform, Lombok
swtp.spring-libraryjava-library + Boot BOM. Boot 플러그인은 적용하지 않음
swtp.spring-boot-appBoot 플러그인, bootJar 단독, 앱간 의존 금지 검증
swtp.spring-cloud-app위 + Cloud BOM, 설정 전파(bus-kafka)

검증의 세기를 구분합니다

"있어서는 안 될 상태"(앱간 의존)는 configuration 시점에 즉시 막고, "아직 안 끝난 상태"(통합테스트 기준형 미보유)는 check에서만 막습니다. 둘을 구분하지 않고 전부 앞에 세우면, 개발 중간 상태마다 빌드가 멈춰서 결국 검증을 꺼 버립니다.

Part Three
공통 자산
앱 11종이 공유하는 것은 유틸리티 모음이 아니라 계약과 기본 동작입니다. 스타터 하나가 무엇으로 이루어지는지, 무엇을 대신해 주는지, 그리고 그 기본값이 어디서 와서 무엇에 지는지까지 봅니다.
libs & Starters

계약 하나, 기본 동작 다섯

libs

swtp-common — 공용 계약

Gateway는 WebFlux, 서비스는 서블릿이라 스타터를 공유할 수 없습니다. 양쪽이 같은 값을 써야만 하는 것만 모읍니다 — SwtpJwtClaims · 헤더명 · AuditorProvider · ErrorCode.

web

응답과 예외의 모양

공통 에러 처리, MDC 필터, 공통 OpenAPI 명세

security

검증 전담 (서블릿)

JWT 검증, @CurrentUser, 통합테스트용 testFixtures. 토큰을 발급하지 않습니다

persistence

DB 접근 기반

JDBC / Flyway / p6spy, BaseEntity, JPA Auditing

kafka

이벤트 봉투

직렬화 기본값, EventEnvelope · 퍼블리셔 · 파서

observability

로그와 메트릭

콘솔 평문 ↔ ECS JSON 전환 + 파일 롤링, Micrometer

도메인 엔티티는 여기 넣지 않고, 보안 스타터는 발급을 하지 않습니다

엔티티가 들어오는 순간 전 서비스가 한 도메인 모델에 묶입니다 — 공용 모듈이 아니라 공용 계약입니다. 같은 이유로, auth-service는 Optional 배포라 검증 측이 서명키를 알면 auth-service 없이 뜰 수 없습니다. 검증 측은 jwks-uri 하나만 압니다 — 발급처가 무엇이든 상관없는 구조가 여기서 나옵니다.

Anatomy

스타터 하나는 다섯 조각입니다

클릭

기본값은 빈이 아니라 프로퍼티로 넣습니다

다섯 스타터의 EPP가 전부 addLast()입니다 — 가장 약한 자리에 놓으므로 앱 yml·환경변수가 언제나 이깁니다. 빈을 @ConditionalOnMissingBean으로 다투게 하는 것보다 이쪽을 먼저 검토합니다.

숫자로 보면

자동구성 클래스 7개 · EnvironmentPostProcessor 5개(스타터당 하나) · @ConfigurationProperties는 2개뿐이고 둘 다 security에 있습니다. 나머지 스타터는 바인딩 클래스 없이 프로퍼티로만 삽니다.

웹 스택을 전파하지 않습니다

spring-boot-starter-webmvc는 compileOnly로 두고 소비 앱이 직접 선언합니다. api로 두면 비웹 앱(gateway·realtime)까지 서블릿에 오염됩니다. 반대로 스타터의 존재 이유인 의존은 api입니다.

Request Path

요청이 들어오는 길에 붙는 둘

swtp-web-starter

응답과 예외의 모양을 고정합니다

역할 — 전역 예외를 ApiResponse 봉투로 바꾸고(GlobalExceptionHandler), 요청 ID를 MDC에 싣고, 게이트웨이 집계 swagger-ui에 맞춘 공통 OpenAPI 명세를 넣습니다.

조건 — SwtpWebAutoConfiguration은 서블릿 웹앱일 때. OpenAPI 쪽은 @ConditionalOnClass가 더 붙습니다.

키 — swtp.openapi.route-prefix 하나뿐이고, 그마저 앱 이름에서 계산해 넣습니다.

하지 않는 것 — 공통 에러는 400·401·500 셋만 붙입니다. 404까지 달면 "목록 조회가 404를 낼 수 있다"는 거짓이 스펙에 실립니다.

swtp-security-starter

검증만 하고, 발급은 하지 않습니다

역할 — JWT 검증 체인(SwtpSecurityAutoConfiguration), 컨트롤러가 Jwt 원본을 보지 않게 막는 SwtpPrincipal, 감사 주체 공급, 통합테스트용 토큰 픽스처.

조건 — 서블릿 + @ConditionalOnClass. swtp.auth.mode가 none이면 리소스 서버를 아예 얹지 않습니다.

키 — SwtpAuthProperties와 SwtpSecurityProperties. 스타터 통틀어 @ConfigurationProperties는 이 둘뿐입니다.

하지 않는 것 — 서명키를 갖지 않습니다. 공개키로만 검증하므로 발급처가 무엇이든 상관없습니다. 발급은 auth-service 몫입니다.

리스트 프로퍼티는 병합이 아니라 치환이라, 목록을 둘로 나눠 두었습니다

그래서 permit-all-paths(플랫폼)와 public-paths(앱 추가분)를 따로 받아 합집합을 씁니다. 하나로 뒀다면 auth-service가 로그인 경로 한 줄 추가하려다 actuator·문서 경로를 통째로 날립니다. 같은 종류가 하나 더 — Boot 4.1은 기본 보안 체인을 세 곳에서 등록하므로 @AutoConfiguration(before=…)에 셋을 모두 적습니다. 빠뜨리면 actuator까지 401입니다.

Data Path

데이터가 오가는 길에 붙는 둘

swtp-persistence-starter

감사 컬럼과 DDL 소유권을 규약으로 굳힙니다

역할 — JDBC·Flyway·p6spy 전파, BaseEntity 감사 컬럼 규약, JPA Auditing 배선.

조건 — 본체는 무조건. SwtpJpaAuditingAutoConfiguration만 조건이 두 겹입니다 — 클래스패스만 보면 JPA 인프라보다 먼저 켜져 기동이 깨집니다.

키 — EPP가 ddl-auto=none · open-in-view=false · 풀 크기 10을 넣습니다. 감사 주체 기본값은 SYSTEM.

하지 않는 것 — JPA를 강제 전파하지 않습니다. telemetry·job은 JdbcClient만 씁니다.

swtp-kafka-starter

봉투 하나로 이벤트 모양을 통일합니다

역할 — 직렬화 기본값, 모든 메시지를 감싸는 EventEnvelope, 발행 파사드 SwtpEventPublisher, 수신측 EventEnvelopeParser.

조건 — @ConditionalOnClass(KafkaTemplate). 퍼블리셔는 그 빈이 실제로 있을 때만 뜹니다.

키 — 직접 만드는 키가 없습니다. 표준 spring.kafka.*에 직렬화·group-id·auto-offset-reset을 넣을 뿐입니다.

하지 않는 것 — ProducerFactory 같은 팩토리를 재정의하지 않습니다. 재시도·acks·SSL 같은 Boot의 프로퍼티 표면을 그대로 남깁니다.

협력하는데, 서로를 의존하지 않습니다

감사 컬럼의 "현재 사용자"는 security가 만들고 persistence가 씁니다. 그런데 둘 사이 컴파일 의존은 0개입니다 — 경계 인터페이스 AuditorProvider를 swtp-common에 뒀기 때문입니다.

벌크 UPDATE는 감사 컬럼을 우회합니다

JPQL update와 네이티브 SQL은 AuditingEntityListener를 타지 않습니다. 컨슈머 쪽 대응물은 문자열로 받아 명시 파싱하는 규약입니다 — 타입 헤더 방식은 소비측을 발행측 클래스명에 묶습니다.

observability의 실질은 자동구성이 아닙니다

SwtpObservabilityEnvironmentPostProcessor가 logging.config·프로메테우스 노출·메트릭 태그를 넣고, logback XML 3종이 포맷을 가릅니다. 자동구성 클래스는 현재 마커 빈만 등록합니다 — 채워질 자리로 남겨 둔 것을 채워진 것처럼 말하지 않습니다.

포맷은 스위치 하나로 갑니다

SWTP_LOG_FORMAT이 plain(기본)이냐 ecs냐에 따라 읽을 logback 파일 자체가 달라집니다. 파일 appender는 어느 쪽에서도 평문입니다 — 수집기가 읽지 않는 사람용 백업이라 이중 적재를 막습니다.

스타터가 전파하지 않아도, 다른 의존이 끌고 들어옵니다

gateway는 eureka-client가 딸고 오는 서블릿 스택을 exclude로 잘라냅니다. 들어오는 순간 Boot가 웹 타입을 SERVLET으로 판정해 게이트웨이 자동구성이 에러 없이 통째로 꺼집니다 — 기동은 성공하고 라우팅만 사라지므로 아무도 모릅니다.

Proof

관측 백엔드를 통째로 갈아 끼웠는데
앱 코드는 0줄 바뀌었습니다

Prometheus · Grafana · Loki ──▶ Elasticsearch · Kibana · Beats

고객사 요구사항이 ELK를 강제해 관측 스택 전체를 철거하고 교체했습니다. 그때 swtp-observability-starter를 쓰는 Java 앱 11종의 코드 변경은 0줄이었습니다.

스타터를 해체하지 않은 이유

로깅(포맷 전환·파일 롤링)과 메트릭 노출이 둘 다 벤더 중립이기 때문입니다. 스타터가 담은 것은 "Grafana에 보내는 법"이 아니라 "표준 형식으로 내보내는 법"이었습니다.

이것이 자산화의 핵심 지표입니다

공통 모듈이 진짜 자산인지 아닌지는, 바깥이 바뀌었을 때 안이 몇 줄 바뀌는가로 판정됩니다. 0줄이면 그 경계는 옳게 그어진 것입니다.

같은 교훈의 반대편

철거된 Prometheus는 설정 파일 마운트 경로가 이미지가 읽는 경로와 달라 오래 방치돼 있었습니다. 마운트도 기동도 성공하고 설정만 무시되는 상태라 아무도 몰랐습니다.

추적

원격이 앱 로컬을 이깁니다

그래서 규칙이 하나 따라옵니다 — 앱마다 달라야 하는 값은 config-repo에 쓰지 않습니다. 실제 반례가 있습니다: eureka.client.register-with-eureka를 거기 두면 discovery-server가 자기 자신에게 등록을 시도합니다.

스타터가 값을 계산하기도 합니다

API 문서 경로는 spring.application.name에서 -service를 떼어 게이트웨이 라우트와 맞춥니다. 손으로 여덟 서비스에 적으면 어긋나는 순간 조용히 404가 됩니다.

통합 테스트는 이 경로를 끊고 시작합니다

spring.config.import를 빈 값으로 덮지 않으면 개발 PC에 떠 있는 config-server가 테스트 결과를 좌우합니다. 함께 swtp.auth.mode=internal도 명시합니다 — 운영 기본값이 none이라 빠뜨리면 "토큰 없으면 401" 방어 테스트가 그냥 통과합니다.

Package Convention

계층이 아니라 도메인이 최상위입니다

com.mo.swtp.master
├── tag/            ← 도메인이 2개 이상인 앱만
│   ├── web/  service/  repository/
│   ├── dto/       Request / Response record
│   └── domain/    Entity · 도메인 이벤트 · enum
├── prcs/  eqp/  fclt/
├── support/       도메인을 모르는 것 (잎)
├── query/         도메인 2개 이상 합치는 조회
└── event/         Kafka 릴레이 · 토픽 상수

  web ─▶ service ─▶ repository ─▶ domain
  누구나 ─▶ support   support는 잎이다

  <도메인A> ──✗──▶ <도메인B>
  타입 직접 참조 금지 — ID(String)로만 잇는다

왜 도메인이 위인가

변경은 거의 항상 도메인 단위로 옵니다. 그리고 나중에 도메인을 서비스로 떼어낼 때 디렉토리째 옮길 수 있어야 합니다. 도메인이 1개면 그 단계를 생략합니다 — 빈 껍데기를 만들지 않습니다.

도메인 간 타입 직접 참조 금지

Eqp.fcltId·EqpTag.eqpId가 전부 String 스칼라이고, DDL도 FK 제약을 걸지 않습니다. @ManyToOne을 하나 들이면 되돌리는 것이 스키마 논쟁이 됩니다.

검사하는 자동 장치는 없습니다

ArchUnit 미도입 — 리뷰가 유일한 그물입니다. 솔직하게 문서에 그렇게 적어 뒀습니다.

Data Ownership

물리 DB는 공유하되, 소유권은 서비스별로

스키마 생성과 테이블 DDL의 주인이 다릅니다

스키마 자체는 infrastructure/postgresql/init/01-schemas.sql이 만듭니다(10종). 테이블 DDL은 각 서비스의 Flyway가 단독 소유합니다.

스키마 지정 방식이 앱마다 다릅니다

JPA를 쓰는 master·ems·auth는 hibernate.default_schema, JdbcClient를 쓰는 telemetry·job은 connection-init-sql: SET search_path입니다. hikari.schema는 경로를 통째로 대체해 ext 확장이 조용히 사라지므로 쓰지 않습니다.

소유권은 규약으로만 지켜집니다

DB 권한으로 막지 않습니다. 그래서 다른 서비스에서 남의 스키마에 INSERT/UPDATE하는 코드가 보이면 그 자체가 결함입니다. 명시적 예외는 operation 하나 — 제어 이력 공용 write 스키마이고, DDL 소유만 master-service가 갖습니다.

그래서 서비스끼리는 DB가 아니라 계약으로 잇습니다

  • HTTP — 화면이 기다리는 조회, 즉시 응답이 필요한 제어 요청, Gateway를 통과하는 모든 외부 요청
  • Kafka — 계측 수집, 도메인 변경 알림, Job·AI·설비 이벤트, 설정 전파
  • 기준은 하나입니다 — 지금 답이 필요한가, 흘려보내면 되는가

Response를 Kafka 페이로드로 재사용하지 않습니다

하는 순간 REST 응답 스키마가 토픽의 와이어 계약이 되어, 프론트 요청 하나가 컨슈머를 깹니다.

프론트엔드는 Kafka에 직접 붙지 않습니다

실시간 데이터는 realtime-service가 컨슘해서 WebSocket/SSE로 내보냅니다. 브라우저를 브로커에 직접 연결하면 인증·백프레셔·토픽 노출이 전부 문제가 됩니다.

Runtime Discipline

런타임을 가로지르는 네 축

01 / 설정

config-repo가 단일 출처

  • 앱은 config-server 없이도 뜹니다 — optional:configserver:
  • 원격 값이 앱 로컬을 이깁니다. 그래서 앱마다 달라야 하는 값은 여기 쓰면 안 됩니다
  • 환경 차이는 host/port로만 흡수
02 / 인증

게이트웨이가 통과시켜도 서비스가 다시 검증

  • 스위치는 2값 — internal / none
  • 서명 오류는 401, JWKS 조회 실패는 503
  • WebSocket은 30초 단기 티켓
03 / 관측

수집기가 읽는 경로는 stdout 단독

  • stdout은 수집용, 파일 롤링은 감사·백업용 — 이중 적재를 막습니다
  • 정수장 식별자를 ECS 표준 슬롯에 적재
  • 중앙 집계 전환 비용은 .env 한 줄
04 / 배포·테스트

차이는 "어떤 컨테이너를 띄우는가"뿐

  • compose --profile은 무엇을 띄울지, Spring 프로파일은 무엇을 읽을지 — 섞지 않습니다
  • 통합 테스트는 운영과 같은 이미지의 Testcontainers
  • 토큰은 testFixtures로 — auth-service를 띄우지 않습니다

다만, 지금 흐르는 것은 한 줄뿐입니다

동기 HTTP 호출은 아직 0건이고, Kafka도 telemetry.raw → realtime 하나만 가동 중입니다. 나머지는 토픽과 계약만 서 있는 상태입니다. 다음 장의 채점은 이 사실 위에서 읽어야 합니다 — 계획을 실적으로 치지 않습니다.

Architecture Style

기능은 나눴는데, 이건 마이크로서비스입니까

모놀리스──── 모듈러 모놀리스── ▲ 우리──── 마이크로서비스
Monolith

경계를 지키는 것이 없다

패키지와 계층으로 나누기는 합니다. 다만 그 선을 넘는 것을 막는 장치가 없습니다 — 남의 테이블을 직접 조인하고 남의 서비스를 그대로 주입해도 컴파일이 됩니다. 시간이 지나면 경계는 그림으로만 남습니다.

Modular Monolith

경계는 있고, 규율이 지킨다

모듈이 자기 데이터를 소유하고 ID로만 서로를 부릅니다. 그러나 DB는 공유하고 릴리스는 원자적입니다. 경계를 강제하는 것은 컴파일러가 아니라 합의입니다.

Microservices

경계가 물리적으로 강제된다

서비스마다 DB가 다르고, 남의 데이터에 닿을 방법이 API밖에 없습니다. 독립 릴리스가 실제로 일어납니다.

판정 — 논리 아키텍처는 모듈러 모놀리스, 물리 토폴로지는 마이크로서비스

프로세스는 11개로 나뉘어 있지만 데이터·릴리스·규모 가정은 전부 모놀리스입니다. 교과서 이름을 붙이면 distributed monolith 구간이고, 이것은 사고가 아니라 제약에서 나온 의도적 선택입니다 — 다음 장에서 축별로 채점합니다.

프로세스를 나눈 이유는 확장성이 아닙니다

auth·autonomous·pms가 정수장 계약에 따라 배포되지 않습니다. 단일 배포 단위 모놀리스로는 이 요구를 만족할 수 없습니다 — 여기가 분리의 유일하고 충분한 정당화입니다.

두 걸음이면 판정이 움직입니다

  • ① 서비스 간 통신 실장 — 런타임 결합이 DB 공유에서 API·이벤트 경계로 옮겨갑니다. 계약은 이미 서 있으니 남은 것은 실장입니다
  • ② 서비스별 DB 롤 + 스키마 단위 GRANT — 데이터 소유가 규약에서 강제로 바뀝니다
  • 그러면 남는 모놀리스 축은 릴리스 단위뿐이고, 그건 단일 서버·모노레포라는 전제에서 나온 의도입니다

남은 리스크 — 스키마 소유권은 강제되지 않습니다

  • 전 서비스가 같은 DB 계정(swtp_dba) 하나로 접속합니다. search_path는 기본값일 뿐 울타리가 아닙니다
  • 지금까지 크로스 서비스 스키마 접근은 0건입니다 — 규율이 지켜지고 있다는 뜻입니다
  • 다만 막는 장치가 없어 첫 1건은 언제든 들어올 수 있고, 들어와도 빌드·테스트가 알려주지 않습니다
  • 대응 후보 — 스키마 단위 GRANT, 또는 ArchUnit 도입

  3. 의존은 apps → starters → libs 한 방향입니다. 앱끼리는 HTTP·Kafka로만 잇습니다.
  4. 규칙은 빌드가 지킵니다. 지키지 못하는 규칙은 규칙이 아닙니다.
  5. 이것은 모듈러 모놀리스에 가깝습니다. 그리고 어디로 갈지도 알고 있습니다 — 통신 실장과 권한 분리, 두 걸음입니다.
